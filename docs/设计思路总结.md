# 业务写路径与异步边界：一次设计取舍总结

> 日期：2026-11-06  
> 项目：台球厅管理系统 / AI 员工层  
> 一句话：先问“这个结果会不会被下一步读到”；会，留在主路径；不会，放旁路，并准备补偿。

---

## 0. 五分钟版

这套系统里的写操作，不需要全部“马上完成”，也不能全部“放进队列慢慢做”。真正要分的是两类：

1. **会影响下一步判断的写操作**：开台、关台、建单、收款、加商品/扣库存。  
   它们的结果必须同步落库，成功之后才能返回。否则下一次开台会抢桌，下一次结账会算错钱，下一单会超卖。

2. **只用于记录和追溯的写操作**：业务日志、核心备份、审计、统计、通知。  
   它们不参与业务判断，可以慢一点、失败不回滚，但必须能查出来、补回来。

判断标准只有一句话：

> **这个结果会不会成为下一步操作的判断依据，或者客人当场必须看到？**

会，就放主路径；不会，才放旁路。

库存是最不能放旁路的例子。如果扣库存进了“第二层”，下一个客人买的时候就要同时看数据库和待办队列，库存就有了两个事实源；为了避免超卖，最后会演变成一套“预占库存”系统。为了让客人少等几十毫秒，维护两套事实，不划算。

所以：

- 库存、桌台、支付留在 MySQL 事务里，保持强一致；
- 日志、备份、审计走旁路，允许失败；
- 旁路失败要有检查、有补录，不能“允许失败”变成“永远缺着”；
- 现在这个项目不需要 Redis，也不需要为了简历硬加一个缓存层；
- 如果以后要学异步/Redis，先做“事务性 outbox + worker”，再把队列换成 Redis Streams。

技术不是越多越好。能说清楚“为什么不用”，本身就是设计能力。

---

## 1. 最初的困惑

最开始的想法是：给项目加一点“厉害的技术”，比如异步处理、Redis 缓冲池，让简历更好看。

这个想法本身没有错。异步、缓存、消息队列都是真本事。但做着做着会发现一个问题：

> 如果为了让技术栈好看，把本来必须马上正确的数据放进异步队列，系统会变得更脆弱，而不是更厉害。

比如库存。客人买完商品，账单已经算出来了，但库存扣减还在队列里。这时候下一个客人来买，系统应该相信哪个数？

- 只看数据库？可能超卖。
- 数据库 + 队列一起看？那就要处理待办记录的顺序、重复、失败、超时、取消。
- 给商品加“预占库存”？那又是一套新的状态机。

问题不是“能不能做”，而是“为了什么做”。如果只是为了简历上多一个 Redis 关键词，这套复杂度不值得。

所以这次真正想清楚的，不是“怎么用 Redis”，而是：

> **哪些数据是事实源，哪些只是记录；哪些结果必须马上算数，哪些可以事后补。**

## 2. 先把几个词说明白

| 词 | 大白话 |
|---|---|
| 主路径 | 必须马上正确、否则下一步会出错的那条路 |
| 旁路 | 记录、备份、统计、通知这类辅助动作 |
| 事实源 | 最终以谁为准；同一个事实只能有一个权威来源 |
| 强一致 | 写完立刻能读到，后面的判断不会看到旧值 |
| 最终一致 | 现在可能还没写完，但过一会儿会补上 |
| outbox | 在数据库里放一张“待办事件表”，先保证事件不丢，再由 worker 处理 |

在这套系统里，库存、桌台状态、订单支付状态是事实源。日志、备份、统计不是事实源，它们是对事实的副本或描述。

事实源只能有一个。多一个“看起来也是真的”的地方，就多一套对账逻辑。

---

## 3. 核心判断标准

判断一个写操作该不该同步，不看它“重不重要”，而看两件事：

1. **它的结果会不会成为下一步业务判断的输入？**
2. **客人是不是当场必须看到这个结果？**

只要占一条，就放主路径，在返回成功之前落库；两条都不占，才放旁路。

```text
这个结果会被下一步操作读到吗？
  ├─ 会 → 主路径：同步、事务、成功才返回
  └─ 不会 → 客人当场必须看到吗？
        ├─ 会 → 主路径
        └─ 不会 → 旁路：可延迟、失败不回滚、可补偿
```

这里要说明一点：

> “同步”是指每一步的结果在返回前落库，不等于整个结账流程必须是一个大事务。

关台、建单、收款仍然是分步的：关台成功后再建单，建单成功后再确认收款。每一步都必须落库，但不需要把三步硬塞进一个事务。这样某一步失败时，系统还能保留上一步的状态，知道进行到哪了。

## 4. 两类写操作

| 类型 | 例子 | 谁要读这个结果 | 失败会怎样 | 放在哪里 |
|---|---|---|---|---|
| 桌台状态 | 开台 / 关台 | 下一次开台要检查桌是否空闲；客人要看台灯、账单 | 抢桌、现场状态和系统不一致 | 主路径，同步 |
| 账单与支付 | 建单 / 收款 | 算账依赖待结算数据；付完才能离场 | 客人不知道付多少，或者没付就能走 | 主路径，同步 |
| 库存 | 加商品 / 扣库存 | 下一单要检查库存够不够 | 超卖 | 主路径，同步，和记消费同一事务 |
| 业务日志 | 每次操作写一行 | 人排查、审计 | 少一条记录 | 旁路，可延迟 |
| 核心备份 | 关台后备份台费 | 事后修复、对照 | 少一份副本 | 旁路，可延迟 |
| 统计 / 通知 | 报表、提醒 | 经营分析、运营 | 晚一点看到 | 旁路，可延迟 |

### 开台和台灯

开台不是只改数据库。客人开了台，现场的台灯要亮；下一次开台又要检查这张桌是不是空闲。

所以桌台状态必须在返回成功之前落库。如果以后真的接硬件，顺序应该是：

1. 先落库，确认这张桌已经属于当前客人；
2. 再发开灯指令；
3. 如果开灯失败，标记“待处理”并告警/重试，不能悄悄告诉客人“开好了”。

数据库说开了、现场没开，和数据库没开、现场开了，都是问题。前者需要补偿，后者需要回滚或人工处理。

### 关台、建单、收款

关台要算台费，客人当场要知道多少钱；收款要确认支付状态，没付完不能让客人走。

这三步每一步都是主路径，但它们是分步的：

```text
关台（写关台时间、算出台费）
  → 建单（把消费合并成一张未支付订单）
  → 收款（把订单标记为已支付）
```

每一步成功后再做下一步。某一步失败，保留已完成的状态，让店员知道进行到哪了；不要假装三步是一个原子操作。

## 5. 库存为什么不能放第二层

这是整个讨论里最关键的的反例。

假设：

- 商品库存是 10 瓶；
- 客人 A 买 10 瓶，账单已经算好，但“扣库存”被放进第二层待办；
- 客人 B 又来买 8 瓶。

如果系统只看数据库，库存还是 10，B 也能买，最后卖出 18 瓶，超卖。

如果系统要看“数据库 + 待办”，那就要回答一堆问题：

- 待办里的扣减，哪些已经成功、哪些还没成功？
- 同一个扣减被重试了两次，算一次还是两次？
- 待办失败后，是回滚账单，还是让客人补钱？
- 待办超时了，库存要不要释放？
- 两个客人同时买，待办之间的顺序怎么定？

最后你会得到一套“预占库存 + 释放 + 对账”的系统。它不是不能做，而是为了省几十毫秒，付出了一整套分布式状态的复杂度。

所以库存必须留在主路径。当前的做法是对的：

```sql
UPDATE products
SET `库存` = `库存` - %s
WHERE id = %s AND `库存` >= %s;
```

这条更新和“插入商品消费”在同一个事务里。更新不到行（库存不够），整笔回滚；两个请求同时扣，也不会把库存扣成负数。

一句话：

> 让客人等几十毫秒的数据库事务，比让系统长期维护两套事实便宜得多。

## 6. 日志和备份为什么可以放宽

日志和核心备份不一样，它们不参与开台、关台、收款、库存的判断。

### 业务日志

日志是给人和审计看的。某一条日志写失败，不应该让客人开不了台、结不了账。

当前代码里的 `one_write_business_log` 就是这么做的：捕获异常，失败只打印提示，不抛异常，不阻断主流程。

但要注意：如果某天日志变成了“收款的唯一凭证”，它就不再是旁路了。这个系统里，订单支付状态在数据库里，日志只是旁证，所以可以放宽。

### 核心备份

可以把 `core_backup` 想成关台小票的复印件：

- 主表先写原件（桌号、开台时间、关台时间）；
- 再复印一份放到 `core_backup`；
- 复印件没打出来，不影响关台，客人照样能走；
- 但以后查账时会发现少了一份。

当前关台流程是：关台事务提交成功之后，再单独尝试备份。备份失败不回滚关台，只在返回信息里说明。这是对的。

### “允许失败”不等于“放任缺失”

既然允许备份失败，就必须回答：失败之后怎么发现、怎么补？

最小的做法是：

1. **查**：找出“已经关台、但 `core_backup` 没有对应记录”的台位费；
2. **补**：从主表把缺失的那一行补进 `core_backup`。

要查两个地方：

- `ongoing_table_fees`：已关台、但还没建订单的台位费；
- `order_table_fees`：已经进入订单的台位费。

因为建订单后，原来的 ongoing 行会被删除，只查第一处会漏掉历史缺口。

判断“缺没缺”的依据是 `consumption_id`：

```sql
-- 已关台、还没进订单
SELECT f.consumption_id, f.`桌台编号`, f.`开台时间`, f.`关台时间`
FROM ongoing_table_fees f
LEFT JOIN core_backup b ON b.consumption_id = f.consumption_id
WHERE f.`关台时间` IS NOT NULL
  AND b.consumption_id IS NULL;
```

```sql
-- 已经进订单
SELECT f.consumption_id, o.`桌台编号`, f.`开台时间`, f.`关台时间`
FROM order_table_fees f
JOIN orders o ON o.order_id = f.order_id
LEFT JOIN core_backup b ON b.consumption_id = f.consumption_id
WHERE b.consumption_id IS NULL;
```

补录时只写 `core_backup`，不碰业务表；按 `consumption_id` 去重，重复执行不会重复插入。先 dry-run 看一眼，再真正写。

### 顺便说清楚：它不是容灾

`core_backup` 和主业务表在同一个 MySQL 里。它能防的是“某一次备份写入失败”，防不了“MySQL 实例、磁盘或主机整体损坏”。

就像原件和复印件放在同一个抽屉里，抽屉丢了，两份都没了。

真正的容灾至少要做到：

- 备份放到独立磁盘、另一台机器或对象存储；
- 有定期全量备份和保留策略；
- 定期做恢复演练：把备份恢复到测试库，跑一遍一致性检查；
- 如果要求恢复到任意时间点，还要开启 binlog 并归档。

对这个项目，最低成本的做法是：每天 `mysqldump` 一份，复制到另一块盘或云盘；每月真正恢复一次，确认备份可用。只导出、不恢复演练，不能算验证过。

## 7. 为什么不需要 Redis

先分清目标：

- 如果目标是“把台球厅系统做稳”，Redis 可以不进；
- 如果目标是“学 Redis”，那应该另找旁路场景，不要改库存主路径。

### Redis 适合放哪里

| 场景 | 是否适合 | 原因 |
|---|---|---|
| 商品列表、桌台概览的读缓存 | 适合 | 读多写少，短 TTL，失效策略清楚 |
| 日志/备份/通知/AI 审计的异步队列 | 适合 | 不参与业务判断，失败可重试 |
| `action_id` 幂等键、接口限流 | 适合 | 天然带 TTL，适合短期状态 |
| 库存扣减的缓冲池 | 不适合 | 下一单要读，强一致，容易变成两个事实源 |
| 桌台状态的唯一来源 | 不适合 | 开台/关台要立刻看到，丢了会抢桌 |
| 支付结果的唯一来源 | 不适合 | 钱不能最终一致 |

### 为什么小项目不急着上 Redis

这套系统是单店、小数据量、单 MySQL。现在的同步事务已经能保证正确性，响应时间也不是瓶颈。

引入 Redis 会增加：

- 部署和运维成本；
- Redis 挂了怎么办；
- 缓存和数据库不一致怎么办；
- 双写失败怎么补偿；
- 测试和排查的复杂度。

如果这些成本换不来明显的收益，就是“为了技术而技术”。

### “不用”不是“不会”

面试时，面试官更怕的是：明明库存是强一致，你为了用 Redis 把它做成最终一致，然后解释不清超卖怎么办。

你能说出“库存不能进第二层”，这本身就是比“我会用 Redis”更稀缺的判断。

## 8. 如果要落实，最小方案

不需要一上来就做队列。按下面四步走，每一步都能独立成立。

### 第一步：把规则写下来

在文档或代码注释里明确：

- 哪些写操作是主路径；
- 哪些是旁路；
- 主路径失败怎么返回；
- 旁路失败怎么发现、怎么补。

这份总结就是第一步的产物。

### 第二步：主路径事务化

- 开台/关台/建单/收款/扣库存，成功才返回；
- 库存用条件更新，防止并发超卖；
- 结账可以分步，但每一步都要落库，不能假装原子成功。

### 第三步：旁路失败不回滚

- 日志写失败只提示，不阻断；
- 核心备份失败只提示，不回滚关台；
- 旁路函数不要让异常冒到主流程。

### 第四步：给旁路加补偿

- 一条只读检查，找出“主表有、副本没有”的记录；
- 一个补录脚本或人工修复流程，从主表补副本；
- 补录要幂等，先 dry-run，再真正写。

做完这四步，你的系统就已经有“同步主路径 + 可补偿旁路”的雏形了。没有 Redis，也没有消息队列，但思路是完整的。

## 9. 如果以后真的要做异步/Redis

如果目标是学习，建议按这个顺序，不要一上来就改主流程。

### 9.1 先做事务性 outbox（不用 Redis）

在主业务事务里，顺便写一条“待处理事件”：

```text
关台事务
  ├─ 更新关台时间、金额（业务表）
  └─ 插入 outbox_events（pending）
```

然后有一个 worker：

```text
worker 读取 pending 事件
  → 写 business.log / core_backup / AI 审计
  → 成功：标记 done
  → 失败：增加 retry_count，稍后重试
  → 超过次数：标记 dead，告警，人工处理
```

关键点：**outbox 在 MySQL 里，和业务状态同一个事务**。即使 worker 挂了，事件还在；重启后可以继续处理。

### 9.2 再把队列换成 Redis Streams

outbox 仍然是事实源，Redis Streams 只是传输层：

- 生产者把 outbox 事件推到 Stream；
- 消费者组处理，成功后 ack；
- 失败进入 pending，重试；
- Redis 丢了也不怕，outbox 还能重新推。

这样你既用到了 Redis，又没有把 Redis 变成业务事实源。

### 9.3 Redis 还可以做这些

- 商品列表、桌台概览的读缓存；
- AI `action_id` 的幂等键，带 TTL；
- 接口限流；
- 多实例下的会话存储。

但库存数量、桌台状态、支付状态，仍然以 MySQL 为准。

## 10. 面试/简历怎么讲

不要写“我用了 Redis”如果实际没用；也不要为了关键词硬加一个缓存层。

可以这样讲：

> 我把系统写操作按“结果是否成为后续判断的输入”分为主路径和旁路：开台、关台、收款、库存扣减放在 MySQL 事务里保证强一致；业务日志、核心备份、审计走可失败、可补偿的旁路。库存没有放入异步缓冲，因为下一单销售必须读到最新库存，否则会产生第二事实源和超卖风险。AI 写操作统一经过 controller，通过两阶段确认、幂等键和审计日志防止误操作。

这段话证明了三件事：

1. 你懂业务和事务边界；
2. 你懂一致性和失败处理；
3. 你会做取舍，不是堆技术。

如果面试官问“为什么不用 Redis”，就回答：

> 这个项目的读量和并发不需要 Redis；库存和桌台状态又是强一致读依赖，放 Redis 会引入双写和缓存一致性问题。Redis 更适合放在旁路队列、缓存和幂等键上。如果以后要做异步，我会先用 outbox 保证事件不丢，再用 Redis Streams 做传输。

## 11. 常见误区

| 误区 | 实际情况 |
|---|---|
| 技术越新越厉害 | 能解决问题的技术才厉害；不解决问题的新技术只是负担 |
| 所有写操作都应该异步 | 会影响下一步判断的写操作必须同步 |
| 日志/备份失败无所谓 | 可以失败，但必须能发现、能补 |
| 有 `core_backup` 就是容灾 | 同一个数据库里只是副本，不是容灾 |
| Redis 做库存缓冲更高并发 | 除非你能处理预占、释放、对账，否则更容易超卖 |
| 同步就是慢 | 几十毫秒的数据库事务，通常比一套分布式补偿更便宜 |
| 简历上技术越多越好 | 面试官更看重你为什么选、怎么验证、失败怎么办 |

---

## 12. 今天的结论清单

- [x] 库存、桌台、支付是主路径，必须同步、强一致。
- [x] 日志、核心备份、审计是旁路，可以延迟、失败不回滚。
- [x] 旁路失败必须能检查、能补录，不能永远缺着。
- [x] `core_backup` 是副本，不是容灾；容灾要独立存储和恢复演练。
- [x] 当前项目不需要 Redis，不需要为了简历硬加缓存层。
- [x] 如果以后学异步，先 outbox + worker，再考虑 Redis Streams。
- [x] 面试讲“取舍和边界”，比讲“用了什么中间件”更有说服力。

最后留一句话：

> **先问结果会不会被下一步读到；会，留在主路径；不会，放旁路，并准备补偿。**

技术不是越多越好。把边界想清楚，比把技术栈堆长更重要。
