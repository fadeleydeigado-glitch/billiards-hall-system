# 热点抢购 A/B 对比压测：内存发牌与异步落库

> 记录日期：2026-11-17  
> A 路：`POST /products/consumption` 纯 MySQL 同步事务  
> B 路：`POST /flash-sale/products/consume` 内存发牌 + 单线程异步落库  
> 对照基线：`2026-11-17-stock-write-baseline.md`  
> 原始结果：`2026-11-17-flash-sale-ab-benchmark.json`

## 1. 结论

本次验证达到“入口削峰”目标，但没有提高最终数据库写入吞吐：

- 50 并发入口的 p99 从基线约 537–546 ms 降到 114–179 ms；
- 入口吞吐从基线约 217 req/s 提升到 657–1681 req/s；
- 打给后台 worker 的 1000 个任务需要约 9.8–11.7 秒才排空，
  worker 平均落库速率约 82–88 req/s；
- 八个正式轮次和一次抢光场景全部完成最终一致性核对，无丢单、重单或超卖。

因此，新链路的价值是把瞬时写入压力搬到后台队列，让入口快速返回 ticket；
它不是让 MySQL 的总写入速度变快。对需要立即看到订单结果的场景，仍需保留
原同步接口。

## 2. 测试环境与口径

测试环境与第一步基线一致：

| 项目 | 配置 |
|---|---|
| 主机 | 本机 Windows 11 |
| Python | 3.12.14 |
| API | FastAPI + Uvicorn，单进程 |
| MySQL | 8.4.9 |
| 应用主库连接池 | 10 |
| 测试库 | `billiards_hall_test` |
| 并发矩阵 | 1、10、25、50 |
| 请求数 | 50、300、500、1000 |
| 重复轮数 | 2 |
| 每轮顺序预热 | 10 |
| 正式请求总数 | 3700 |

测试口径：

- 每轮预热与正式请求数之和等于预先拆分的商品牌数量，确保正式压测不会因售罄
  走到拒绝分支；
- 入口延迟只覆盖 HTTP 校验、内存 `popleft`、ticket 创建和入队，不等待数据库；
- `drain_after_burst_seconds` 从正式请求全部返回后开始计时，到 worker 队列
  清空、processing=false、所有 ticket 离开 queued 为止；
- `worker_average_rate_per_second` 使用“正式请求数 ÷ 入口到排空总耗时”，
  是偏保守的后台实际平均速率；
- 分位数使用 nearest-rank 口径。

复现命令：

```powershell
$env:MYSQL_DATABASE = "billiards_hall_test"
$env:MYSQL_BACKUP_DATABASE = "billiards_backup_test"
$env:ALLOW_WRITE_TESTS = "1"
python scripts/bench_flash_sale_ab.py `
  --port 8011 `
  --scenarios "1:50,10:300,25:500,50:1000" `
  --repeat 2 `
  --warmup 10 `
  --label flash-sale-ab-vs-mysql `
  --json-output docs/benchmarks/2026-11-17-flash-sale-ab-benchmark.json
```

脚本要求 API 使用测试库，并建议为每轮压测新启动 API 进程，避免上轮专用桌台
已经进入本地配置缓存。

## 3. 阶段一：高并发入口接单性能

### 3.1 50 并发重点 A/B

表中同时给出两轮范围和两轮中位数，避免只展示最好一轮。

| 指标 | A：纯 MySQL 同步 | B：内存发牌入口 | 中位数变化 |
|---|---:|---:|---:|
| p50 | 188.46–190.93 ms | 25.22–73.66 ms | 189.69 → 49.44 ms，约 3.8× 更快 |
| p95 | 405.92–417.45 ms | 41.03–95.60 ms | 411.68 → 68.31 ms，约 6.0× 更快 |
| p99 | 537.24–545.66 ms | 114.29–179.12 ms | 541.45 → 146.70 ms，约 3.7× 更快 |
| 吞吐 | 216.68–217.49 req/s | 656.87–1680.52 req/s | 约 5.4× 提升 |

B 路两轮差异明显：第一轮 p50 73.66 ms、吞吐 656.87 req/s；第二轮 p50
25.22 ms、吞吐 1680.52 req/s。即使采用较差的第二轮之外的第一轮数据，
入口 p99 仍比 A 路基线低约 67%，吞吐仍约为 A 路的 3 倍。该波动会原样保留在
JSON 中，不作为生产 SLA。

### 3.2 完整并发梯度

下表使用两轮中位数：

| 并发 | A p50 | B p50 | p50 提升 | A p99 | B p99 | p99 提升 | A 吞吐 | B 入口吞吐 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 6.17 ms | 1.03 ms | 6.0× | 22.02 ms | 9.32 ms | 2.4× | 150.83 | 685.16 |
| 10 | 39.34 ms | 14.27 ms | 2.8× | 175.69 ms | 27.34 ms | 6.4× | 255.46 | 669.68 |
| 25 | 81.77 ms | 35.20 ms | 2.3× | 174.46 ms | 71.63 ms | 2.4× | 274.12 | 678.40 |
| 50 | 189.69 ms | 49.44 ms | 3.8× | 541.45 ms | 146.70 ms | 3.7× | 217.08 | 1168.70 |

入口吞吐在约 650–720 req/s 附近较稳定；50 并发第二轮达到 1680.52 req/s，
属于本机合成测试中的上冲样本。

### 3.3 超卖抢光秒拒

单独预热 5 张商品牌，使用 20 并发同时抢：

| 指标 | 结果 |
|---|---:|
| 接受 ticket | 5 |
| 售罄秒拒 | 15 |
| 其他错误 | 0 |
| p50 | 18.35 ms |
| p95 | 25.08 ms |
| p99 | 25.51 ms |
| 入口吞吐 | 724.03 req/s |
| accepted p50 | 13.38 ms |
| rejected p50 | 21.69 ms |

队列内发牌本身是内存操作；客户端观测到的约 18–26 ms 包含 HTTP、线程调度和
本机压测框架开销。抢光后没有进入后台任务，15 个拒绝请求没有产生 ticket。

## 4. 阶段二：后台排空与最终一致性

### 4.1 排空数据

| 并发 | 请求数 | 爆点后队列积压 | 爆点后排空 | 入口到排空总耗时 | worker 平均速率 |
|---:|---:|---:|---:|---:|---:|
| 1 | 50 | 40–44 | 0.22–0.31 s | 0.30–0.39 s | 129.59–168.00 req/s |
| 10 | 300 | 264–273 | 1.85–2.02 s | 2.31–2.45 s | 122.34–129.88 req/s |
| 25 | 500 | 453–457 | 3.53–3.67 s | 4.22–4.46 s | 112.18–118.37 req/s |
| 50 | 1000 | 908–945 | 9.84–11.67 s | 11.36–12.27 s | 81.51–88.02 req/s |

50 并发时，入口约 0.6–1.5 秒接收完 1000 个任务，但后台还需要约 10–12 秒排空。
这正是“削峰填谷”的直接证据：前端等待被缩短，数据库写入被单线程拉平。

### 4.2 数据一致性

八个正式轮次的所有 ticket 最终均为 `succeeded`，`failed=0`。每一轮均逐项核对：

- 商品库存等于初始库存减成功 ticket 数；
- `ongoing_product_consumptions` 行数等于成功 ticket 数；
- 消费数量合计等于成功 ticket 数；
- `idempotency_records` completed 行数等于成功 ticket 数；
- 商品 outbox 事件数等于成功 ticket 数。

正式轮次共 3700 个成功 ticket，加上 80 个预热 ticket，共完成 3780 次异步
落库；抢光场景另有 5 个成功 ticket。全部一致性检查通过。

## 5. 架构演进收益

从纯 MySQL 同步事务演进到当前形态，得到三类收益：

1. **入口抗突发**：HTTP 不再等待数据库事务，ticket 入队后立即返回。
2. **发牌边界清晰**：内存牌保证尝试资格数量；最终库存仍由 MySQL
   `库存 >= 数量` 条件更新决定，内存牌不是库存事实源。
3. **失败可回收**：业务失败和重试耗尽的 ticket 有明确状态，未消费的牌子会
   回到队尾；老路开台/关台仍同步摘牌和补牌。

本地 TTL 缓存解决的是配置型读数据重复读取；内存发牌解决的是瞬时写入口排队。
两者职责不同，没有把库存、桌台实时状态或支付状态放进 TTL 缓存。

## 6. 工程权衡

本次结果不能解释成“数据库吞吐提升 5 倍”：

- 入口吞吐和后台落库吞吐必须分开看；
- 50 并发下 worker 平均约 82–88 req/s，低于同步基线约 217 req/s；
- 大突发会有秒级到十几秒的最终一致性窗口；
- 单 worker 是明确的下游瓶颈，但也是有序、易排查的刻意选择；
- 内存池、ticket 和队列只在单进程内，重启会丢失，不能直接用于多实例生产；
- 管理接口当前无登录和权限控制；
- 若上生产，应优先考虑持久化队列/Redis、worker 横向扩展、ticket 持久化和
  告警，而不是继续扩大内存牌数量。
