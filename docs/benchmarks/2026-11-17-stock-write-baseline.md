# 加商品扣库存写接口基线

> 记录日期：2026-11-17  
> 测试目标：当前未加入缓存、内存队列或 Redis 的纯 MySQL 写链路。  
> 接口：`POST /products/consumption`  
> 结论：所有正式请求成功，数据一致性校验通过；在 50 并发、同一商品行竞争时，
> p95 约 0.41 秒，吞吐约 217 req/s。继续增加并发没有提高吞吐，系统在本次测试中
> 已进入数据库写入与连接池排队阶段。

## 1. 测试环境

| 项目 | 配置 |
|---|---|
| 主机 | 本机 Windows 11，16 个逻辑处理器 |
| Python | 3.12.14 |
| API | FastAPI + Uvicorn，1 个进程，未开启 `--reload` |
| MySQL | 8.4.9 |
| 事务隔离级别 | `REPEATABLE-READ` |
| `innodb_flush_log_at_trx_commit` | `1` |
| `innodb_buffer_pool_size` | 128 MiB |
| MySQL `max_connections` | 151 |
| 应用主库连接池上限 | 10 |
| 测试库 | `billiards_hall_test` |
| 专用数据 | 桌台 `B99`、商品 `PBENCH01` |

## 2. 测试链路

每个请求实际完成以下工作，不只是执行一条 `UPDATE`：

1. FastAPI 参数和请求头校验；
2. 控制器读取桌台配置、商品资料；
3. 检查库存和商品是否可售；
4. 事务内写幂等占位；
5. 插入待结算消费主表和商品明细；
6. 使用 `库存 = 库存 - 1 WHERE 库存 >= 1` 原子扣库存；
7. 写商品备份 outbox 事件；
8. 完成幂等记录并提交事务。

所有正式请求购买同一个商品，因此这是库存写链路的强竞争场景，也是最直接的压力
基线。它不是不同商品分散写入的乐观场景。

## 3. 测试方法

- 每个压测线程保持一条 HTTP 长连接，并在连接内依次发请求。
- 每轮正式测试前顺序预热 10 次。
- 每轮生成独立幂等键，避免把幂等回放误当成重复写入。
- 每轮库存为 `预热数 + 正式请求数 + 20`，保证测试期间不会因库存不足失败。
- 正式测试矩阵为 `1 / 10 / 25 / 50` 个并发线程，共重复 2 轮。
- 分位数采用 nearest-rank 口径。
- 每轮结束后核对库存、待结算消费、幂等记录和 outbox 行数，随后清理测试数据。

复现命令：

```powershell
$env:MYSQL_DATABASE = "billiards_hall_test"
$env:MYSQL_BACKUP_DATABASE = "billiards_backup_test"
python scripts/bench_stock_writes.py `
  --port 8011 `
  --scenarios "1:50,10:300,25:500,50:1000" `
  --warmup 10 `
  --repeat 2 `
  --label pure-mysql-stock-baseline `
  --json-output "docs/benchmarks/2026-11-17-stock-write-baseline.json"
```

## 5. 数据一致性

两轮共执行 8 个正式场景，正式请求 3700 次，预热请求 80 次，共 3780 次写请求。
全部成功，没有 HTTP 错误、业务错误、超时或库存不足。

每轮均核对通过：

- 最终库存等于初始库存减去成功请求数；
- `ongoing_consumptions` 行数等于成功请求数；
- `ongoing_product_consumptions` 行数等于成功请求数；
- `idempotency_records` 的 completed 行数等于成功请求数；
- `outbox_events` 行数等于成功请求数。

压测结束后再次检查，专用商品、桌台和带专用前缀的幂等记录均为 0，没有残留。

## 6. 结果解读

1. **单线程 p50 约 6.2 ms。** 这说明请求包含完整事务、幂等和 outbox 写入后，
   单请求延迟仍然是毫秒级。
2. **10 并发的第一轮有明显冷启动影响。** p99 达到 311.64 ms，第二轮恢复为
   39.75 ms。一个可能原因是顺序预热只使用了一条数据库连接，第一轮 10 并发时才
   集中建立连接池中的其余连接；本次测试没有单独采集连接建立耗时，因此不把原因
   写成已证实结论。两轮都必须保留，不能只报第二轮。
3. **稳定吞吐峰值出现在 10 并发附近。** 第二轮达到约 349 req/s；并发升到 25 和
   50 后，吞吐没有继续提高。所有请求抢同一个商品行，行锁串行化是限制因素之一；
   应用连接池上限 10 也会让更高并发在池外排队。
4. **50 并发的主要问题是尾延迟。** p50 仍低于 200 ms，但 p95 已超过 400 ms，
   p99 超过 500 ms。后续优化应优先降低排队和尾延迟，不能只看吞吐。

## 7. 使用边界

- 这是本机 localhost 合成压测，不代表生产 SLA。
- API 和 MySQL 共用同一台机器，会互相争抢 CPU 和磁盘。
- 所有请求写同一个商品行，是刻意制造的最强库存竞争场景。
- 测试使用单个应用进程和 10 条数据库连接；改变进程数或连接池参数后需要重新测。
- 本结果可以作为后续缓存、预扣、队列或 Redis 方案的对照基线，但不能据此宣称
  “高并发”或线上 QPS。
