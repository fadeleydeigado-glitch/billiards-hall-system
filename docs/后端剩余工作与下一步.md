### 几个容易误解的点

**连接池真的做完了。**  
不是只改了依赖，`one_get_mysql_connection()` 和备份库连接都已经从池里取。本机 10 并发 × 200 次请求的压测记录里，`/frontend/refresh` 的 p50 从约 432ms 降到约 28ms，p95 从约 530～575ms 降到约 44ms。这个数字只能说明本机读接口的连接开销变小了，不能写成“高并发”。

**请求校验和错误码也做完了。**  
不是只有设计，`backend/schemas.py`、`backend/errors.py` 和 `backend/api_layer.py` 都已经接上。字段缺失、类型错误、资源不存在、状态冲突、数据库异常，已经有不同的 HTTP 状态码。

**应用账号已经换了。**  
当前 `.env` 里是 `MYSQL_USER=billiards_app`，数据库授权也只覆盖业务需要的库表。`.env` 没有被 Git 跟踪，历史里也没有提交过。旧密码是否已经彻底失效，这次没有验证；如果还没做，建议找机会确认一次。

本轮检查结果是 `pending=0`、`processing=0`、`dead=0`。这只能说明现在没有排队和死信，不代表故障路径已经演练过。

## 4. 每项大概怎么做

### 4.1 提交当前改动

当前工作区有一批已跟踪文件被修改，另有多个新文件/目录未跟踪。先把它们分组提交，不要一直堆着。

建议拆成三个提交：

```text
feat: add pooled MySQL connections and refresh benchmark
feat: add request schemas and HTTP error mapping
test: cover id generation and API validation
```

提交前至少跑：

```powershell
python -m compileall -q backend tests scripts
python -m unittest tests.test_api_errors tests.test_request_schemas tests.test_id_utils tests.test_decimal_money tests.test_product_backup
node --test frontend/tests/frontend.test.mjs
```

### 4.2 加 `/health` 和请求 ID

不要搞复杂，两个小接口就够：

- `GET /health`：只表示“进程还活着”，返回 200 和四键结构；
- `GET /ready`：执行一次 `SELECT 1`，数据库连不上就返回 503。

请求 ID 用一个中间件生成 UUID，做两件事：

- 响应头加 `X-Request-ID`；
- 业务日志每行带上这个 ID。

不要在健康检查里返回数据库密码、连接串或完整异常堆栈。

### 4.3 补 API 路由级测试

现在 `tests/test_api_errors.py` 测的是“错误类型到状态码”的映射，`tests/test_request_schemas.py` 测的是模型本身；还缺“从 FastAPI 路由打进去”的测试。

建议加 `tests/test_api_routes.py`，用 FastAPI `TestClient` 覆盖：

- 非法 JSON → 400；
- 缺字段、类型错、数量小于等于 0 → 422；
- 桌台不存在 → 404；
- 桌已占、订单已付 → 409；
- 成功返回金额是字符串，不是浮点数。

验证类测试可以不连数据库；业务状态类测试可以用 monkeypatch 替换 controller 返回值，避免写库。

### 4.4 做一次 outbox 故障演练

在测试库做，不要拿正式库试：

1. 把备份库指向一个不可用地址，或者暂时停掉备份库；
2. 在测试库执行一次关台/加商品；
3. 确认主业务成功，`outbox_events` 里有 `pending` 或重试记录；
4. 恢复备份库，再跑 worker，确认事件变成 `done`；
5. 确认备份表里数据正确，没有重复行。

然后再加一个很小的告警脚本：

```text
dead > 0                 -> 退出码 1
最老 pending 超过 10 分钟 -> 退出码 1
否则                     -> 退出码 0
```

用 Windows 任务计划或 Linux cron 每 5 分钟跑一次，比“等我想起来看”可靠。

### 4.5 做一次备份恢复演练

这是备份真正算数的时刻：

1. 把 `billiards_backup` 导出成 SQL 文件；
2. 恢复到临时库，例如 `billiards_backup_restore_test`；
3. 把环境变量指向临时库，跑备份缺口检查和数据巡检；
4. 对一下关键行数、金额和 id；
5. 记录恢复耗时和结果。

不要直接覆盖正式备份库。恢复演练的目标是“证明备份可用”，不是“在生产环境冒险”。

## 5. 索引这件事已经有结论

本轮对两个核心查询跑了 `EXPLAIN`：

- 首页刷新：`billiards_tables`、`ongoing_consumptions`、`ongoing_table_fees` 都走了索引；`ongoing_product_consumptions` 因为表很小，走了全表扫描。
- 未支付订单：`orders` 按支付状态走了索引，明细表按主键/外键关联；排序阶段有 `Using temporary; Using filesort`。

现在数据量很小，`filesort` 不是瓶颈，**不需要为了“看起来专业”马上加复合索引**。等有真实慢查询或数据量上来，再按实际 SQL 加索引并用 `EXPLAIN` 对比。

## 6. 这个项目现在可以怎么讲

如果投纯后端，建议用这个口径：

> 单店台球厅店务系统，FastAPI + MySQL + Vue 3，落地开台、加商品、关台、建单、收款五条写流程。开台用 `SELECT ... FOR UPDATE` 和事务内二次检查防抢桌；关台、收款、库存扣减用条件更新防重复和超卖；金额全链路 `Decimal`；核心备份用事务性 outbox + 独立 worker，支持重试、死信和缺口补录。后端加了 MySQL 连接池，本机 10 并发只读压测 p50 从约 432ms 降到约 28ms；请求模型和 HTTP 错误码已补齐，配套 54 个 Python 单测和 7 个前端测试。

不要写：

- “高并发”：只有本机 10 并发读接口压测；
- “SaaS”：没有租户隔离；
- “AI 员工已上线”：现在决定不做，只有历史设计文档；
- “QPS 提升 X 倍”：压测范围有限，写 p50/p95 就够了；
- “生产级”：还没有登录、监控、部署和恢复演练。

如果投纯后端岗位，BOSS 文案里用“纯后端版”那段，AI 设计只当设计经历，不要写成正在开发。
