# 轻量可观测性方案说明

> 范围：`/health`、请求 ID、慢查询日志  
> 目标：用最小改动回答两个问题——服务活没活？这条日志对应哪次请求？  
> 原则：先解决“出问题能查”，不引入复杂平台，不改业务表，不改业务逻辑。

---

## 0. 一页看懂

| 要解决的问题 | 这次的做法 | 改完后的效果 |
|---|---|---|
| 服务活没活 | 增加 `GET /health` | 返回 200 就说明 API 进程还能响应 |
| 日志对应哪次请求 | 每个请求生成或复用 `X-Request-ID` | `access.log`、`business.log`、`slow_query.log`、`error.log` 都带同一个编号 |
| 哪条 SQL 慢 | 在连接池层统一计时 | 超过 200ms 的 SQL 自动写入 `slow_query.log` |
| 控制台错误会消失 | MySQL 异常和未捕获异常写文件 | 窗口关了也能在 `error.log` 里查 |

这次明确不做：

- 不做 `/ready`；
- 不做 `/status` 汇总页；
- 不做 `operation_audit` 审计表；
- 不做登录和操作人；
- 不接 ELK、Loki、Sentry、Prometheus；
- 暂时不做复杂日志轮转，先简单追加。

默认参数：

- 慢查询阈值：200ms，可用环境变量 `SLOW_QUERY_MS` 调整；
- 请求 ID 格式：`req_` + 16 位十六进制；
- 客户端传入合法的 `X-Request-ID` 时复用，否则服务端生成；
- 静态资源和 `/health` 不写 `access.log`，避免刷屏。

怎么读这份文档：

- 只想快速了解：看第 0、2、3、4、12 节；
- 想知道为什么要这么设计：看第 1、6、7、8 节；
- 想知道具体怎么落地：看第 9、10、11 节；
- 想知道现在代码改到哪了：看第 14 节。

## 1. 现在的问题

### 1.1 没有健康检查

现在访问 `/` 只是返回前端 HTML。即使 MySQL 已经挂了，`/` 仍然可能返回 200。监控只能知道“端口还在”，不知道“这个 API 进程还能不能正常工作”。

### 1.2 日志无法按一次请求串起来

现在只有开台、关台、加商品、创建订单、确认收款这五个写流程会写 `business.log`。格式是：

```text
[2026-11-11 10:00:00] [人] [开台] [桌号=1] [成功]
```

问题有三个：

- 时间只精确到秒，两个人同一秒操作，日志分不清谁是谁；
- 没有请求编号，用户说“刚才那单失败了”，无法精确找到那一次；
- 读接口没有业务日志，刷新页面、查商品、查未支付订单这些操作没有记录。

### 1.3 数据库错误只输出到控制台

现在 `one_convert_mysql_error()` 只是 `print()` 一行。服务如果以隐藏窗口、Windows 服务、计划任务等方式运行，控制台输出很可能没人看到，窗口一关记录就没了。

### 1.4 没有慢查询证据

现在的 28ms、44ms 是手工压测结果，不是运行时观测。某天页面突然变慢，只能靠重现和猜，无法回答“哪个接口、哪条 SQL、哪次请求慢”。

### 1.5 连接池在导入时就连接数据库

原来 `PooledDB` 写在模块顶层，导入 `backend/io_layer.py` 就会尝试连接 MySQL 和备份库。MySQL 没启动时，API 可能连启动都失败；备份库没启动时也会拖累主服务。这和“备份库故障不阻断前台开台”的目标是矛盾的。

轻量版会把连接池改成懒加载：第一次真正需要数据库时才创建。这样 MySQL 暂时没启动，API 进程仍能启动并响应 `/health`。

## 2. 功能一：`/health`

### 2.1 它回答什么

`GET /health` 只回答一件事：**API 进程还活着，还能接收并响应 HTTP 请求。**

返回 200，响应体保持项目统一的四键结构：

```json
{
  "status": "success",
  "error_type": null,
  "data": {
    "status": "ok"
  },
  "message": "服务正常"
}
```

### 2.2 它不回答什么

`/health` 不检查数据库，不检查备份库，不检查磁盘、CPU、内存，也不检查业务数据是否正确。

数据库通不通是 `/ready` 的职责。这次按最小闭环不做 `/ready`，所以 `/health` 返回 200 只代表“进程活着”，不代表“现在能开台”。

### 2.3 为什么不做 `/ready`

`/ready` 会额外引入数据库探测、超时、连接池、503 响应等一堆细节。现在只要求“知道服务活没活”，`/health` 已经够用。

以后如果要做，`/ready` 再用一条 1～2 秒超时的独立连接执行 `SELECT 1`，成功 200、失败 503。那是下一步。

### 2.4 边界

- 整台机器关机、端口没监听、进程崩了，`/health` 访问不到；
- 进程活着但事件循环被长时间阻塞，`/health` 可能超时；
- 数据库挂了，`/health` 仍然返回 200，这是故意的，不是 bug。

## 3. 功能二：请求 ID

### 3.1 它是什么

请求 ID 是“这次操作的流水号”，标识一次 HTTP 请求。它不是消费编号，也不是订单编号。

### 3.2 和消费编号、订单编号的区别

| 对比项 | 消费编号 / 订单编号 | 请求 ID |
|---|---|---|
| 标识什么 | 一条业务记录 | 一次操作或一次 HTTP 请求 |
| 存在哪里 | 业务表 | 响应头和日志 |
| 生命周期 | 跟着业务记录走 | 只属于这一次请求 |
| 操作失败时 | 可能根本没有生成 | 仍然有编号 |
| 主要用途 | 业务查询、对账 | 排查、追踪、把日志串起来 |

一句话记忆：**消费编号标识“哪条业务记录”，请求 ID 标识“哪次操作”。**

### 3.3 具体例子

| 时间 | 操作 | 请求 ID | 业务编号 |
|---|---|---|---|
| 10:00 | 开台 | `req_A` | 生成 `T_1_...` |
| 10:05 | 加商品 | `req_B` | 生成 `S_1_...` |
| 10:10 | 关台 | `req_C` | 更新 `T_1_...` |
| 10:11 | 建单 | `req_D` | 生成订单编号 `1_...` |
| 10:12 | 收款 | `req_E` | 更新订单状态 |

一次请求可能碰到多个业务编号，比如建单会把多条消费合成一张订单；一个业务编号也会被多次请求碰到，比如开台、关台、建单、收款。所以两者不能混。

### 3.4 怎么生成、怎么透传

- 默认生成 `req_` + 16 位十六进制，例如 `req_3f9a2c1b7d4e5f60`；
- 如果请求头自带合法的 `X-Request-ID`，就复用它，方便前端或 AI Agent 追踪；
- 合法格式限制为 8～64 位，只允许字母、数字和 `-_.:`；
- 最终使用的 ID 会写进响应头 `X-Request-ID`。

不信任客户端随便传的值，是为了防止超长字符串、换行或奇怪字符污染日志。

### 3.5 怎么让日志自动带上它

用 Python 标准库的 `contextvars.ContextVar` 存当前请求 ID：

1. 中间件收到请求，生成或复用 ID；
2. 把 ID 放进 `ContextVar`；
3. Service 层、DAO 层、慢查询游标需要写日志时，直接读取当前上下文；
4. 请求结束后清理上下文，避免影响下一个请求。

这样不用给每个函数都加一个 `req_id` 参数，业务函数签名不用改。

FastAPI 的同步接口在线程池里执行，`contextvars` 通常会跟着复制过去；这个要用测试确认。万一某条路径拿不到，再退回 `request.state` 显式传参。

### 3.6 日志里长什么样

`access.log`：

```text
[2026-11-11 10:00:00.123] [req=req_3f9a2c1b7d4e5f60] [POST /tables/open?table_id=1] [200] [28.4ms] [127.0.0.1]
```

`business.log`：

```text
[2026-11-11 10:00:00] [req=req_3f9a2c1b7d4e5f60] [人] [开台] [桌号=1] [成功]
```

`slow_query.log`：

```text
[2026-11-11 10:00:00.456] [req=req_3f9a2c1b7d4e5f60] [slow_query] [duration_ms=523.4] [rows=1] [ok] [sql=SELECT ...] [params=(1,)]
```

`error.log`：

```text
[2026-11-11 10:00:01.789] [req=req_3f9a2c1b7d4e5f60] [MySQL 故障] [读取商品总表] [OperationalError] ...
```

### 3.7 失败的请求也有 ID

参数校验失败、桌台不存在、库存不足、数据库异常，这些请求都可能没有生成任何业务记录，但它们仍然有请求 ID。`access.log` 会记录状态码，`business.log` 会记录写流程的失败原因，`error.log` 会记录技术异常。

### 3.8 “谁做的”要单独说清楚

现在系统没有登录，日志最多只能记录：

- 来源：`人` 或 `AI`；
- 客户端 IP；
- 请求时间、路径、结果。

它不能知道具体是哪个店员。要精确到人，需要加登录、角色和操作人字段，这是另一个功能，不在本次范围内。

## 4. 功能三：慢查询日志

### 4.1 什么算慢

默认超过 200ms 算慢。可以用环境变量调整：

```text
SLOW_QUERY_MS=200
```

这个项目当前压测的 p95 约 44ms，200ms 能过滤正常波动，又能抓住明显异常。觉得太松可以改 100ms，觉得太严可以改 500ms。

### 4.2 在哪里计时

这个项目用的是 PyMySQL，不是 SQLAlchemy，所以没有 `before_cursor_execute` / `after_cursor_execute` 钩子。

等价做法是给连接池传一个自定义 `Cursor` 子类，重写 `execute()` 和 `executemany()`，里面用 `time.perf_counter()` 计时。业务代码一行不用改。

### 4.3 记录什么

每条慢查询记录：

- 时间；
- 请求 ID；
- 耗时（毫秒）；
- 影响行数；
- 成功还是失败；
- SQL 模板（带 `%s` 占位符的原句）；
- 绑定参数（截断）；
- 失败时的异常类型和简短信息。

不记录查询结果集，不记录数据库密码，不把参数拼进 SQL 再打印。

### 4.4 为什么不记所有 SQL

- 日志量会爆炸；
- 正常 SQL 太多，反而找不到重点；
- 磁盘会被占满；
- 排查时只需要看“明显慢”的那几条。

调试时可以临时把 `SLOW_QUERY_MS` 设成 0，让所有 SQL 都落盘；平时不要这么做。

### 4.5 为什么不用 MySQL 自带的 slow log

MySQL 自带的 slow log 也能记录慢 SQL，但它没有请求 ID、没有业务上下文，还要改数据库配置，查起来不方便。

应用层这份慢查询日志能直接回答：**哪次请求、哪个业务动作、哪条 SQL、花了多久。** 两者不冲突，现阶段应用层这份更实用。

### 4.6 示例

```text
[2026-11-11 10:00:00.456] [req=req_3f9a2c1b7d4e5f60] [slow_query] [duration_ms=523.4] [rows=12] [ok] [sql=SELECT id, `每小时价格` FROM billiards_tables] [params=None]
```

### 4.7 边界

`execute()` 的耗时包含网络和数据库执行，不包含 `fetchall()` 把结果搬回 Python 的时间。这个项目结果集很小，够用；以后如果发现大结果集慢，再补 fetch 计时。

## 5. 四个日志文件

### 5.1 各自负责什么

| 文件 | 记什么 | 什么时候记 | 谁写 |
|---|---|---|---|
| `logs/access.log` | 每个 HTTP 请求的摘要：方法、路径、状态码、耗时、请求 ID、客户端 IP | 每个请求，静态资源和 `/health` 除外 | API 进程 |
| `logs/business.log` | 五个写流程：开台、关台、加商品、创建订单、确认收款 | 流程返回后，无论成功失败 | API 进程 |
| `logs/slow_query.log` | 超过阈值的 SQL：耗时、SQL 模板、参数、请求 ID | 超过 `SLOW_QUERY_MS` 时 | API 或 worker |
| `logs/error.log` | MySQL 异常、未捕获异常、堆栈 | 出错时 | API 或 worker |

### 5.2 轮转策略

轻量版先简单追加，不做复杂轮转。原因是单店日志量很小：

- `access.log` 每个请求一行，一天通常只有几百 KB；
- `slow_query.log` 只记慢 SQL，量更小；
- `business.log` 只记五个写流程；
- `error.log` 只记异常。

以后如果日志变大，再把写入改成 `RotatingFileHandler`，例如 10MB × 5 份，或者按天切分。

### 5.3 `.gitignore`

项目已经忽略 `logs/` 和 `*.log`，日志不会进 Git。可以再补一行 `logs/*.log`，让规则更直观。

### 5.4 多进程注意事项

`RotatingFileHandler` 不是多进程安全的。Windows 上两个进程同时轮转同一个文件，可能报“文件被占用”。

轻量版的原则是：一个文件尽量只有一个写入者。`access.log`、`slow_query.log`、`business.log` 主要由 API 进程写；outbox worker 的错误继续写它自己的 `outbox_worker.log`，不要和 API 抢 `error.log`。

以后上多 worker，再换集中日志平台。

## 6. 错误记录：写文件还是写数据库表

### 6.1 技术错误写文件

数据库连不上、SQL 报错、代码异常、堆栈，这些写 `error.log`。

原因很简单：

- 数据库都坏了，写数据库可能也写不进去；
- 写在同一个业务事务里，失败还会跟着回滚；
- 文件独立于数据库，最适合排障。

### 6.2 业务审计可以写数据库表

“谁在什么时候开台、关台、加商品、建单、收款，成功还是失败”，这类是业务审计，可以写数据库表，方便在系统里查询。

但这是“业务审计”，不是“技术错误日志”。技术错误和业务审计不要混在一张表里。

### 6.3 为什么不能写在同一事务

假设加商品时库存不足，业务事务会回滚。如果把“加商品失败”的审计记录写在同一个事务里，它会跟着回滚，最后什么都没留下。

再假设业务成功，但写审计记录时数据库出错。如果审计和业务在同一个事务里，可能把一笔成功的收款或关台回滚掉，这更不可接受。

### 6.4 文件也不是绝对可靠

文件比控制台可靠，但不是绝对可靠：

- 机器或磁盘坏了，本地文件也会丢；
- 进程在写日志前崩溃，这条日志可能没有；
- 多进程同时写同一个文件可能交错。

真要防机器坏，要定期把 `logs` 目录备份到另一台机器或网盘；大厂是实时把日志送到集中日志平台。

### 6.5 `operation_audit` 表的三种做法

以后如果要做 `operation_audit`，有三种选择：

1. **同事务写审计表**：只记录成功操作，业务成功审计一定成功，业务回滚审计也回滚；记录不到失败。
2. **业务返回后，用独立连接写审计表**：失败也能记录；但进程在业务提交后、审计写入前崩溃，可能漏一条。
3. **先写本地文件，再由后台脚本异步导入审计表**：更像 File-based Outbox，能扛数据库短暂不可用；但要做去重、偏移量管理和顺序处理。

本项目现在先不做，等第二步再决定。

### 6.6 本阶段建议

技术日志写文件；业务写流程继续写 `business.log`；`operation_audit` 先不做。先把“出问题能查”解决掉。

## 7. 日志边界：哪些记，哪些不记

| 记录内容 | 记不记 | 写哪里 | 说明 |
|---|---|---|---|
| 每个 HTTP 请求摘要 | 记 | `access.log` | 静态资源和 `/health` 除外 |
| 五个写业务操作 | 记 | `business.log` | 开台、关台、加商品、建单、收款 |
| 4xx 参数或状态错误 | 记摘要 | `access.log`；进入 controller 的写流程也进 `business.log` | 不记堆栈 |
| 5xx 或未捕获异常 | 记详情 | `error.log` | 带堆栈和请求 ID |
| 慢 SQL | 超过阈值才记 | `slow_query.log` | 默认 200ms |
| 每条 SQL | 默认不记 | 调试日志 | 临时把阈值设为 0 才记 |
| 请求体和响应体 | 默认不记 | 不记 | 避免隐私和体积 |
| 健康检查和静态资源 | 默认不记 | 不记 | 避免刷屏 |
| 密码、令牌、支付信息 | 永远不记 | 不记 | 安全底线 |

核心原则：

- 正常请求记摘要；
- 业务写操作记审计；
- 技术错误记详情；
- 慢操作记阈值；
- 敏感内容不记。

不是越多越好。日志太多反而找不到重点，还会占磁盘。

## 8. Outbox 与日志/审计的关系

### 8.1 什么是双写问题

假设关台要做两件事：

1. 主库更新台位费，写上关台时间和金额；
2. 备份库也写一条关台记录。

如果在一个请求里直接写两个库，会出现不一致：

- 主库提交成功，备份库失败：主库关了台，备份库没有；
- 备份库写成功，主库回滚：备份库有一条根本不存在的关台记录。

两个独立数据库没法用一个本地事务同时提交。

### 8.2 Outbox 怎么解决

Outbox 不直接写备份库，而是在主库的同一个事务里，多写一条“待办事件”：

```text
BEGIN
  更新 ongoing_table_fees
  插入 outbox_events（pending）
COMMIT
  ↓
outbox_worker 读事件
  ↓
写备份库（失败重试，按 consumption_id 幂等）
```

这样：

- 主库提交成功，事件一定在；备份库暂时挂了也没关系，worker 后面重试；
- 主库回滚，事件也回滚；不会出现“业务没成，备份库却收到通知”；
- worker 可能重复投递，所以备份写入必须幂等。

这就是 at-least-once + 幂等消费。

### 8.3 为什么日志不能跟着业务事务走

假设加商品时库存不足，业务事务会回滚。如果把“加商品失败”的日志写在同一个事务里，日志也会跟着回滚，最后什么都没留下。

再假设业务成功，但写日志时磁盘满了。如果日志和业务在同一个事务里，日志写失败可能把一笔成功的收款或关台回滚掉，这不可接受。

所以日志的边界必须是：**业务事务提交或回滚之后，再写日志；日志写失败只提示，不影响业务结果。**

### 8.4 镜像对比

| 对比项 | Outbox 事件 | 日志 / 失败审计 |
|---|---|---|
| 和业务事务的关系 | 同一个事务，同生共死 | 事务外，必须独立存活 |
| 业务回滚时 | 事件必须回滚 | 日志必须保留 |
| 第一落点 | 主库的 outbox 表 | 本地文件或独立连接 |
| 可靠性目标 | 至少一次，不能丢 | 尽力而为，不能拖垮业务 |
| 下游 | 备份库、消息队列 | 日志平台、审计表 |

### 8.5 为什么说“文件日志像 Outbox”

因为骨架确实一样：

- 都不直接写慢速或易挂的外部系统；
- 都先在本地留一份：Outbox 是数据库表，日志是本地文件；
- 都有后台搬运工：Outbox 是 worker，日志是 Filebeat、Vector 或自写脚本；
- 都靠异步重试或补送来容错。

所以可以把本地 `.log` 文件理解成 **File-based Outbox**：文件是发件箱，搬运工是日志采集器，审计表或日志平台是下游。

### 8.6 它和真 Outbox 的差别

- 文件写入和业务数据库没有共同事务。业务提交后、日志写入前如果进程崩了，这条日志还是会丢。
- 文件没有 ACID、没有唯一约束、没有回滚。要防重复，需要自己加事件 ID，并在下游去重。
- 文件在本地磁盘，磁盘坏了也会丢。
- 多进程同时写同一个文件会交错，轮转也可能冲突。

所以：用文件做技术日志合适；用文件做“绝对不能丢”的审计，就要接受它只是尽力而为，或者再加一层可靠投递。

### 8.7 大厂怎么做

大厂一般讲“三根柱子”：

- 日志：结构化日志，统一收集到 ELK、Loki 这类平台，设级别、采样和保留期；
- 指标：错误率、延迟、连接数做成监控面板和告警，Prometheus、Grafana 那一套；
- 链路追踪：一个请求经过多个服务，用 trace ID 串起来，每个数据库调用是一个 span。

错误另外进 Sentry 这类平台，业务审计进数据库或数仓。它们也不会“所有日志都记”，而是按级别、采样、保留期来控制成本。

这个项目是单店，不需要上这一整套。把原则缩小用：请求 ID 就是迷你 trace ID，本地日志就是迷你日志平台，`/health` 就是迷你监控。

### 8.8 一句话总结

**Outbox 解决“业务状态和待办事件必须同生共死”；日志解决“技术现场必须独立留存、不能拖垮业务”。两者骨架相同，事务边界正好相反。**

## 11. 风险与边界

### 11.1 `contextvars` 传递

FastAPI 同步接口在线程池里执行，`contextvars` 通常会跟着复制过去，但要用测试确认。如果某条路径拿不到，就退回 `request.state` 显式传参。

### 11.2 多进程日志

一个日志文件尽量只有一个写入者。Windows 上多进程同时写和轮转同一个文件可能冲突。现阶段 API 单进程 + outbox worker 分开写各自文件，问题不大。

### 11.3 本地文件会丢

本地文件比控制台可靠，但机器或磁盘坏了也会丢。重要日志要定期备份到另一台机器或网盘；以后上集中日志平台再解决。

### 11.4 `/health` 只代表进程活着

数据库挂了，`/health` 仍然 200。这是设计选择，不是 bug。要知道数据库通不通，需要 `/ready`，这次不做。

### 11.5 慢查询只测 `execute`

`execute()` 的耗时包含网络和数据库执行，不包含 `fetchall()`。如果以后有大结果集，再补 fetch 计时。

### 11.6 请求 ID 的信任问题

客户端传的 `X-Request-ID` 要做格式和长度校验；外网入口不要无条件信任。当前只允许 8～64 位字母、数字和 `-_.:`。

### 11.7 不知道具体操作人

没有登录，只能记录来源和 IP。要精确到人，需要登录、角色和操作人字段，这是另一个功能。

### 11.8 日志量

轻量版是追加写，不做轮转。单店量很小；如果以后日志变大，再加 `RotatingFileHandler` 或集中日志平台。

## 13. 名词表

| 名词 | 大白话解释 |
|---|---|
| 存活检查 / liveness | 进程还活着吗 |
| 就绪检查 / readiness | 现在能干活吗，通常检查数据库 |
| 请求 ID | 这一次 HTTP 请求的流水号 |
| 链路追踪 / trace ID | 一个请求经过多个服务时，把它们串起来的编号 |
| 访问日志 / access log | 每个请求的方法、路径、状态码、耗时 |
| 业务日志 / business log | 开台、关台、加商品、建单、收款这些业务动作 |
| 审计日志 / audit log | 谁在什么时候做了什么，成功还是失败 |
| 慢查询 | 执行时间超过阈值的 SQL |
| Outbox | 事务性发件箱，业务数据和待办事件在同一个本地事务里提交 |
| 双写 | 同时写两个独立系统，容易出现一边成功一边失败 |
| at-least-once | 至少投递一次，可能重复，需要消费方幂等 |
| 幂等 | 同一条消息处理多次，结果和执行一次一样 |
| `contextvars` | Python 的请求上下文变量，用来在线程/协程间传递当前请求 ID |
| 四键结构 | `status`、`error_type`、`data`、`message` 四个固定字段 |
