# 台球厅项目：先用大白话看懂这版

> 这份是“先看这一页”的版本。  
> 想看代码证据和完整清单，再看同目录的《项目架构复盘与改进清单.md》。

## 一句话结论

你的项目不是玩具，也不是“只会 CRUD”的课设。它已经是一个**能完整跑通单店业务的系统**，而且你开始考虑事务、并发、测试和失败处理了。

但它现在还不能直接说成：

- 工业级；
- 高并发；
- 完整 SaaS；
- AI 员工已经上线。

更准确的说法是：

> **一个完成度较高、工程意识明显、但还需要补安全、运维和接口规范的单店全栈项目。**

## 二、模型夸你的话，哪些是真的

### 1. 从 JSON 到 MySQL，不是换了个存储方式

以前数据在文件里，现在在数据库里。你真正做的是：

- 把桌台、订单、库存、支付状态放进了可以约束和查询的地方；
- 把“开台、加商品、关台、建单、收款”变成了五条明确的写流程；
- 让失败时能回滚，而不是留下半条数据。

这是实打实的进步。

### 2. 你的写流程有“防手滑”设计

用大白话说：

- **事务**：一组操作要么全成功，要么全不算数；
- **行锁**：开台时先拿住这张桌子的“钥匙”，别人只能等；
- **条件更新**：只有“还没关台”才能关，只有“还没付款”才能收款，只有“库存够”才能扣；
- **二次检查**：开台前在事务里再看一眼，避免两个前台同时抢到同一张桌。

这些不是概念堆砌，代码里确实做了。

### 3. 你的测试不是摆设

你做了三类检查：

- 10 个底层写函数跑一遍，最后统一回滚；
- 完整业务流程跑一遍，还故意制造“扣库存失败”来看商品消费会不会一起回滚；
- 单独检查数据库里的行数、时间字段、孤儿记录和金额。

大部分个人项目没有这些。

### 4. 你知道“不是技术越多越好”

你没有为了简历硬加 Redis，而是先判断：库存、桌台、支付不能被异步化。这个判断是成熟的。

## 三、模型说过头的地方

### “工业级”

现在缺的东西还不少：

- 没有登录和权限；
- 没有多租户；
- 没有监控和告警；
- 没有独立备份；
- 没有正式的 API 错误契约；
- 没做过真实的并发和故障演练。

所以叫“有生产意识”，不叫“已经生产级”。

### “高并发”

现在是“关键写冲突有保护”，不是“系统支持高并发”。

区别在于：

- 你防住了同一张桌被开两次；
- 但没有测试过 100 个人同时操作会怎样；
- 也没有测试过多台服务器同时跑会怎样。

### “SaaS”

SaaS 至少要有登录、租户隔离、权限和真实支付。现在这些都没有，所以它还是单店系统。

### “AI 员工已经落地”

现在只有设计文档，还没有可以运行的 AI 代码。准确说法是“完成了方案设计”。

## 四、模型提到的三个“小问题”，分别怎么看

| 模型的说法 | 实际情况 | 现在要管吗 |
|---|---|---|
| 两个 MySQL 驱动很冗余 | 主程序用 PyMySQL，查看脚本用另一个驱动，不是同一个连接里混用 | 不着急，可以以后统一 |
| 真实密码泄露了 | 这是真问题，而且比“双驱动”严重得多 | 现在就改密码 |
| 日志里有一次“缺少订单编号” | 只能说明后端拦截了一个坏请求，不能证明前端页面一定会漏传 | 先复现，不要直接改代码 |

## 五、我另外发现的几个真实问题

### 1. 业务层没有完全“只管算账”

你原本希望业务层只做检查和计算，但它现在还会：

- 自己取当前时间；
- 自己调用数据库写备份。

这不会让系统立刻坏掉，但会让业务代码不容易单独测试。以后应该让控制层把时间传进去，把备份写入上移。

### 2. 完整流程测试可能会写到真数据库

`test_full_flow.py` 自己写了“测试数据保留，不清理”。如果没有环境闸门，而 `.env` 又指向真实库，就可能污染真实数据。

这比“代码写得不够漂亮”更值得先修。

### 3. 备份失败了，目前没人事后检查

关台成功后再写 `core_backup`。如果备份失败，关台仍然成功，这是可以接受的；但现在没有工具定期检查“哪些关台记录缺了备份”，也没有安全的补录流程。

### 4. 接口返回“200 成功”，但业务可能失败

比如缺少订单编号，HTTP 仍返回 200，真正的错误放在返回内容里。

当前前端会用 `status` 判断，所以页面能用；但以后接 AI、第三方客户端或网关时，别人可能以为请求成功了。

### 5. 金额计算用了浮点数

台费计算现在是“先浮点相乘，再直接舍弃小数”。通常没问题，但金额边界最好用 `Decimal`，否则可能出现 `59.999999` 被截成 `59` 这种小误差。

### 6. 你还没有认证、权限和生产备份

这些不是当前作业的阻塞项，但如果你要把系统放到公网，或者让别人使用，就必须补。

## 六、现在真正该做什么

不要一口气把所有东西都改完。按这个顺序：

### 今天

1. 改掉曾暴露的数据库密码；
2. 不要再把真实 `.env` 发到聊天里；
3. 确认 `.env` 没有被 Git 跟踪。

### 这周

4. 给 `test_full_flow.py` 加“必须明确允许才能写库”的开关；
5. 写一个只读脚本，检查关台记录是否缺 `core_backup`；
6. 写一个幂等补录脚本，先支持 dry-run。

### 下一步

7. 把业务层的数据库写入和时间获取移出去；
8. 给 API 加请求模型和错误状态码；
9. 用 `Decimal` 重写金额计算；
10. 做一次有记录的小规模并发测试。

### 暂时不要做

- 不要为了简历加 Redis；
- 不要先接大模型再做规则引擎；
- 不要在没有测试库保护时跑完整流程测试；
- 不要把“模型夸你”当成系统已经达到生产级的证据。

## 七、你可以在面试里怎么说

不要背“工业级”“高并发”“SaaS”这种容易被追问的词。

可以这样说：

> 我独立做了一个 FastAPI + MySQL + Vue 3 的台球厅管理系统，完成了开台、加商品、关台、建单、收款五条业务闭环。开台用行锁和事务内二次检查防止抢桌，关台、收款和库存扣减用条件更新防止重复操作和超卖，并用完整流程测试和事务回滚测试验证失败时不会留下半条数据。

这段话没有夸张，而且每一句都有代码和测试支撑。
