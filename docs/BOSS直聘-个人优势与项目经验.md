项目描述：
面向单店台球厅的前台业务系统，覆盖开台、加商品、关台、建单、收款完整闭环，重点解决交易一致性、并发重复操作、金额精度和异步备份可靠性。

主要工作：

1. 架构与边界
按 API、controller、business、IO 四层拆分，统一 status / error_type / data / message 结果协议；business 层只做校验、计算和数据组装，不依赖数据库，当前时间和备份写入由 controller 编排。

2. 交易一致性与并发控制
落地开台、加商品、关台、建单、收款五条写流程。开台使用 SELECT ... FOR UPDATE 锁住桌台行，并在事务内重新读取待结算消费、二次确认空闲；关台使用 关台时间 IS NULL 条件更新，收款使用 支付状态 = '未支付' 条件更新，库存使用 库存 >= 数量 条件更新，防止重复关台、重复收款和超卖；订单、订单明细、待结算消费清扫在同一事务中提交或回滚。

## 六、面试时怎么展开（不要写进 BOSS，留着自己讲）

### 1. 为什么 outbox 能保证备份任务不丢？

关台/加商品和 outbox_events 在同一个 MySQL 事务里提交：业务成功，事件一定存在；worker 再用独立连接写备份库。备份库失败不影响主业务，但事件会退避重试，超限进 dead，另有缺口检查脚本兜底补录。

### 2. 开台怎么防止两个人同时开同一张桌？

事务外先做一次提示性检查；进入事务后用 SELECT ... FOR UPDATE 锁住 billiards_tables 对应行，再用事务内 cursor 重新读取该桌待结算消费，确认没有未关台台位费后才插入。锁和二次检查都在事务内，后到请求会等锁并看到最新状态。

### 3. 关台、收款、扣库存怎么防重复？

不靠应用层“先查再写”，而是把状态条件放进 UPDATE：

- 关台：WHERE 关台时间 IS NULL
- 收款：WHERE 支付状态 = '未支付'
- 库存：WHERE 库存 >= 数量

更新命中 0 行再查一次，区分“不存在”和“状态已变化”，返回不同错误。

### 4. AI 怎么防止乱开台、乱收款？

AI 不直接调 one_*，也不直接生成 SQL；只能调 controller 的白名单工具。写操作先 prepare，服务端保存 action_id、参数哈希、角色和过期时间；用户确认后 execute 再检查归属、权限、过期、幂等和业务状态，最后才调用原 controller。金额由 Decimal 规则引擎计算，模型只负责解释。

### 5. 为什么没有写高并发、SaaS、AI 员工已上线？

因为代码里没有压测、租户隔离、认证和 AI 运行代码。面试时主动说边界，比被追问后承认更稳。

## 七、不要写进 BOSS 的词

- “高并发”：没有压测数据，只能写“关键写冲突有数据库级保护”。
- “工业级”：没有认证、监控、部署验证。
- “SaaS”：没有 tenant_id、登录、角色和租户隔离。
- “AI 员工已上线”：当前只有 `docs/AI_EMPLOYEE.md` 设计文档，没有 `ai/` 运行代码。
- “RAG / LangGraph / Redis 已落地”：依赖清单和代码里都没有。
- “QPS 提升 X 倍 / 准确率 96%”：没有对应压测和评测结果。
