# 数据库账号与权限备忘录

日期：2026-11-10  
项目：台球厅店务管理系统

## 一句话总结

这次把“后端一直用 root 连数据库”改成了三个分开的账号：

- `root`：只管建库、建表、迁移、授权；
- `billiards_app`：后端 API 和备份 worker 日常营业用；
- `billiards_ai`：以后 AI 只读查询用，只能看，不能改。

业务代码没有改，改的是数据库账号、权限和本地配置。

## 1. 为什么从“两个通道”变成了“三个”

一开始想分两个：

- 业务账号：能读写；
- AI 账号：只读。

后来发现 root 也不能和业务混在一起。root 是数据库管理员，能删库、改表、建用户；日常后端根本不需要这些权力。如果 root 密码泄露，整个 MySQL 都危险。

所以最终是三个独立身份，不是三个权限等级：

| 账号 | 像什么 | 主要用途 | 能不能写业务数据 |
|---|---|---|---|
| `root` | 数据库管理员的总钥匙 | 建库、建表、迁移、授权 | 能，但平时不用 |
| `billiards_app` | 前台收银机的门卡 | 后端 API、outbox worker | 能 |
| `billiards_ai` | 只读报表账号 | 以后 AI 查账、查空桌、查库存 | 不能 |

这是按当前项目情况做的分工，不是通用模板：

- 当前网页要开台、关台、收款，所以 `billiards_app` 必须能写；
- 当前 AI 还没有代码，所以 `billiards_ai` 先只给只读权限；
- root 只保留给建库建表这种低频管理操作。

## 2. 三个账号分别能做什么

### root

- 能建库、删库、建表、改表、建用户、授权；
- 只在初始化数据库、迁移、修权限时使用；
- 密码不放进 `.env`，不要给网页后端使用。

### billiards_app

能做：

- 查询桌台、商品、订单、待结算消费、备份记录；
- 开台、加商品、关台、建订单、确认收款；
- 扣商品库存；
- 写和更新 outbox 备份事件；
- 写和更新 idempotency_records 防重记录；
- 删除“待结算”表里的记录（结账清理需要）。

不能做：

- 删订单、删商品、删桌台、删备份记录；
- 建库、删库、建表、改表结构；
- 建用户、改密码、授权；
- 读 `mysql` 系统库。

### billiards_ai

能做：

- 查 `billiards_hall` 和 `billiards_backup` 两个库；
- 查空桌、待结算、订单、库存、备份情况；
- 给以后“老板助手”做只读查询。

不能做：

- 新增、修改、删除任何数据；
- 建库、删库、改表；
- 建用户、授权；
- 读 `mysql` 系统库。

AI 如果要开台、关台、收款，应该调用后端已有的业务接口/controller，不直接用自己的数据库账号写库。

## 3. 为什么应用账号需要“增删改查”

不是给它乱用，而是当前业务确实需要：

- 开台、加商品、建订单 = 新增；
- 查桌台、查消费、查订单 = 查询；
- 关台、收款、扣库存 = 修改；
- 结账后清理待结算记录 = 删除。

所以 `billiards_app` 需要这四类操作，但只限当前业务用到的表，不是整个 MySQL 都能动。

## 6. 列级权限：现在不用学那么深

一句话：

> 列级权限 = 细到“只能改某一列”，比如只能改库存，不能改商品单价。

现在不需要做，原因很简单：

- 当前表级权限已经够用；
- 列级权限维护更麻烦，代码加字段、加查询时容易漏授权；
- 这个项目当前更大的风险是 API 认证和业务规则，不是列级权限。

你只需要记住：

- 以后真要做，只对“商品价格、订单金额”这类高危列做限制；
- 要有一份统一的权限清单和脚本，不要到处手写授权；
- 不要为了“看起来高级”去把每一列都拆开授权。

不需要背 SQL，也不需要现在掌握细节。

## 7. 以后怎么用

- 启动后端：按 README 的 uvicorn 命令启动，`.env` 已经是 `billiards_app`，不用改；
- 建库、建表、迁移：用 root，做完就退出；
- AI 查数据：以后用 `billiards_ai`；
- AI 要开台、关台、收款：让它调后端接口/controller，不直接写数据库；
- 网页报“Access denied”：先检查 `.env` 是不是 `billiards_app`，再看对应功能有没有授权。
