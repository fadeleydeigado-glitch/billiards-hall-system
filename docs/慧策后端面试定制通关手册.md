1. **你的定位不是“假装 Java 选手”，而是“通用后端原理 + Python 工程落地 + 关键业务正确性”。**

   你的项目材料里，真正能证明的是：

   - 已落地：`SELECT ... FOR UPDATE`、事务内二次检查、条件更新、订单/明细/待结算同事务、事务性 outbox、独立 worker、重试/死信/超时回收、按 `consumption_id` 幂等写入、DBUtils 连接池、`Decimal` 金额、测试与巡检。

- **💡 30秒看懂本质（大白话版）**：  
  面试官问 Java，不一定是要求你换语言，而是在借 Java 问“你懂不懂底层”。你可以先给一句标准答案，再补一句 Python 对照，最后落到项目证据。顺序是：**Java 是什么 → Python 对应什么 → 我在项目里怎么保证正确**。  
  不要在不会的细节上硬编；比如没写过 Spring，就明确说“我没有生产级 Spring 经验，但这题考的是循环依赖和容器启动顺序，我可以讲通用机制，以及我在 Python 项目里怎么避免类似耦合。”

- **🔗 结合我的项目怎么讲**：

  | Java 话题 | 一句话标准答案 | Python 对照 | 项目落点 |
  |---|---|---|---|
  | `HashMap` | JDK8 主要是数组 + 链表 + 红黑树，链表过长会树化 | `dict` 是哈希表，常见实现用开放寻址和紧凑索引；Key 必须可哈希 | 用 `dict` 做编号到记录的索引，减少重复遍历 |
  | `ArrayList` | 动态数组，查询快，扩容和中间插入有成本；本身非线程安全 | `list` 也是动态数组 | 批量查询结果在内存里组装，不在循环里查库 |
  | `synchronized` | JVM 层互斥，修饰实例方法锁 `this`，静态方法锁 Class 对象 | `threading.Lock` / `RLock`；进程内锁不跨进程 | 数据库正确性主要靠 MySQL 行锁和条件更新，不靠 Python 进程锁 |
  | `ThreadPoolExecutor` | 核心线程、最大线程、队列、拒绝策略 | `concurrent.futures.ThreadPoolExecutor` | 用连接池限制数据库连接，不用线程数硬顶数据库 |
  | JVM GC | 可达性分析 + 分代回收；常见标记-清除/复制/整理 | CPython 主要是引用计数 + 分代循环 GC | 不把 JVM 参数硬套到 Python，讲清对象生命周期即可 |

- **🎙️ 考场直接背诵话术**：
  > Java 里的 `HashMap` 我会按 JDK8 的数组 + 链表 + 红黑树来答；在 Python 里对应的就是 `dict`，同样是哈希表，但 CPython 的常见实现更偏向开放寻址，Key 必须是可哈希对象。项目里我不是为了背数据结构而用 `dict`，而是把一次批量查询的结果按 `consumption_id` 建索引，避免在循环里反复查数据库。线程安全也是一样：`ArrayList` 本身不安全，Java 里会用并发容器或外部同步；Python 里 `list` 也不是线程安全的，但我的关键写路径没有靠进程内锁，而是靠 MySQL 的行锁、条件更新和事务来保证跨请求正确性。

- **💻 核心代码/SQL 速记**：

  ```python
  # Python 中“先批量查，再在内存里建索引”的常见写法
  rows = load_rows_by_ids(ids_from_request)       # 一次查询
  row_by_id = {row["id"]: row for row in rows}    # 避免 N+1
  ```

## 📌 考点 10：MySQL 索引有哪些

- **🗣️ 面试官原话汇总**：
  - 图2：“mysql索引有哪些”
  - 图6：“mysql索引数据结构”
  - 图8：“MySQL数据库中索引为什么能加速查询？（B+树原理）”

- **💡 30秒看懂本质（大白话版）**：  
  索引就是书的目录。没有目录，你找“第 8 章”只能从第一页翻；有目录，你先定位页码，再去那一页。数据库索引也是如此：它把“按某个字段查找”从全表扫描，变成沿着有序结构快速定位。  
  但目录不是越多越好：每次插入、删除、更新，目录也要维护；索引还会占空间。所以索引是“用写入成本和空间，换读取速度”。

- **🔗 结合我的项目怎么讲**：

  - 主键 `order_id`、`consumption_id` 是 InnoDB 聚簇索引，订单/明细按主键查找最快。
  - `orders` 有 `idx_orders_status`、`idx_orders_time`，适合按支付状态、时间筛选。
  - `ongoing_table_fees` 和 `ongoing_product_consumptions` 有 `idx_..._table`，开台/关台时按桌号找待结算记录。
  - `outbox_events` 有 `(status, next_retry_at, event_id)` 联合索引，worker 领取 pending 事件时正好按这个顺序过滤和排序。
  - 这里要诚实：当前索引是按业务查询设计的，不等于已经做过大规模线上调优；如果面试官追问，我会说“我会用 `EXPLAIN` 验证，而不是凭感觉说命中”。

- **🎙️ 考场直接背诵话术**：
  > MySQL 常见索引按用途分，有主键索引、唯一索引、普通索引、联合索引、全文索引和空间索引；按 InnoDB 的存储结构分，又可以分为聚簇索引和二级索引。InnoDB 的主键索引叶子节点直接放整行数据，二级索引叶子节点通常放主键值，所以通过二级索引查整行时可能要“回表”。项目里订单按 `order_id` 查、待结算消费按桌号查、outbox 按状态和重试时间领取，都是按真实查询路径建索引。索引不是越多越好，因为写入要维护索引，而且优化器不一定选它；最终要看 `EXPLAIN` 的 `type`、`key`、`rows` 和 `Extra`。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 常见索引类型
  PRIMARY KEY (id)
  UNIQUE KEY uk_order_no (order_id)
  KEY idx_status_time (支付状态, 创建时间)

  -- 看表上有哪些索引
  SHOW INDEX FROM orders;
  ```

## 📌 考点 11：为什么是 B+ 树，不是二叉树/哈希

- **🗣️ 面试官原话汇总**：
  - 图8：“MySQL数据库中索引为什么能加速查询？（B+树原理）”
  - 图6：“mysql索引数据结构”

- **💡 30秒看懂本质（大白话版）**：  
  数据库的数据在磁盘上，最贵的动作不是比较两个数字，而是“去磁盘拿一页数据”。二叉树每个节点只有两个孩子，树会很高，查一次要跳很多层；B+ 树一个节点能放很多 key，像“多层目录”，树很矮，一次 I/O 能排除一大片数据。  
  B+ 树的非叶子节点只存索引键，叶子节点存数据或主键，并且叶子之间用链表串起来。所以它既能快速等值查找，也能做范围查询和排序。

- **🔗 结合我的项目怎么讲**：

  - `orders` 按 `order_id` 查是主键等值查询，走聚簇索引。
  - 查“某段时间的订单”适合走时间索引做范围扫描。
  - 查“未支付订单列表”如果只看 `支付状态`，选择性可能不高，优化器可能宁愿全表扫；更合理的是把状态和时间做成联合索引，或分页限制扫描量。
  - `outbox_events` 的 `(status, next_retry_at, event_id)` 是为了让 worker 先按状态过滤，再按重试时间排序，减少扫描和排序成本。

- **🎙️ 考场直接背诵话术**：
  > InnoDB 默认用 B+ 树，不是为了“听起来高级”，而是为了减少磁盘 I/O。B+ 树的非叶子节点只存键，扇出很大，树高低；叶子节点按键有序并相互连接，所以等值查询、范围查询和排序都友好。InnoDB 的主键索引是聚簇索引，叶子节点放整行；二级索引叶子节点放主键，查不在索引里的列可能要回表。代价是写入要维护树结构，所以索引要围绕真实查询建，不能每个列都来一个。项目里 outbox 的联合索引就是按 worker 的查询顺序设计的：先 status，再 next_retry_at，再 event_id。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 观察访问类型和实际使用的索引
  EXPLAIN
  SELECT event_id
  FROM outbox_events
  WHERE status = 'pending'
    AND next_retry_at <= UNIX_TIMESTAMP()
  ORDER BY event_id
  LIMIT 20;
  ```

- **💡 30秒看懂本质（大白话版）**：  
  索引像按姓名排序的电话簿。你查“张三”，很快；你查“名字里第二个字是三的人”，电话簿的顺序帮不上忙，只能一页页翻。数据库也一样：一旦你在索引列上套函数、做隐式类型转换、用前置模糊匹配，或者联合索引不从最左列开始，优化器就可能放弃索引。

  但“失效”不是绝对判决。小表、低选择性列、返回大量行时，优化器可能主动选择全表扫描，因为走索引再回表反而更贵。面试时要说“可能不走索引”，不要背成“永远失效”。

- **🔗 结合我的项目怎么讲**：

  - 按 `order_id`、`consumption_id` 精确查，走主键。
  - 如果写 `WHERE DATE(FROM_UNIXTIME(创建时间)) = '2026-11-13'`，时间列被函数包住，普通时间索引很难用；应改成时间范围：`创建时间 >= 开始 AND 创建时间 < 结束`。
  - 如果查 `WHERE 商品名称 LIKE '%可乐%'`，前置 `%` 不能利用普通 B+ 树的有序性。
  - 联合索引要遵守最左前缀；例如 `(status, next_retry_at, event_id)`，只按 `next_retry_at` 查通常不能完整利用这个索引。
  - 订单状态只有很少几个值，单独用 `支付状态` 的区分度不高，优化器可能不选它；这也是为什么要结合时间和分页。

- **🎙️ 考场直接背诵话术**：
  > 常见的索引失效或“可能不走索引”的场景有几类：第一，索引列上做函数、运算或隐式类型转换，比如把时间戳转成日期再比较；第二，`LIKE '%xxx%'` 这种前置模糊匹配；第三，联合索引不满足最左前缀；第四，`OR` 两侧有一边没有可用索引；第五，优化器判断回表成本太高，或者表很小、选择性很低，主动选全表扫描。我的处理方式不是背口诀，而是用 `EXPLAIN` 看 `type`、`key`、`rows`、`filtered` 和 `Extra`。比如项目里按时间范围查订单，我会保留原始 BIGINT 时间戳做范围条件，避免对列套函数。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 不推荐：索引列被函数包住
  WHERE DATE(FROM_UNIXTIME(创建时间)) = '2026-11-13'

  -- 推荐：保留列本身，做范围查询
  WHERE 创建时间 >= 1762963200
    AND 创建时间 <  1763049600
  ```

## 📌 考点 16：左连接、右连接、全连接、内连接

- **🗣️ 面试官原话汇总**：
  - 图1：“左连接右连接全连接内连接举例说明区别”
  - 图1：“给定两张表，左连接和内联结的查询结果范围”
  - 图7：“左连接和内联结”

- **💡 30秒看懂本质（大白话版）**：  
  把两张表想成两个班级名单：

  - 内连接：只保留两边都对得上的人（交集）。
  - 左连接：左表全员保留，右表有就补上，没有就填 `NULL`。
  - 右连接：右表全员保留，左表没有就填 `NULL`。
  - 全连接：两边全员都保留，谁没匹配上，另一边填 `NULL`。

  MySQL 没有原生的 `FULL OUTER JOIN`，需要 `LEFT JOIN ... UNION ... RIGHT JOIN ...` 模拟。

- **🔗 结合我的项目怎么讲**：

  - 订单主表 `INNER JOIN order_product_consumptions`：只查有商品明细的订单。
  - `LEFT JOIN`：以订单为主，即使没有明细也保留订单；或者以主表台费为主，左连接备份表找“缺备份”的记录。
  - 找备份缺口：

    ```sql
    SELECT f.consumption_id
    FROM order_table_fees f
    LEFT JOIN core_backup b
      ON b.consumption_id = f.consumption_id
    WHERE b.consumption_id IS NULL;
    ```

  - `WHERE b.consumption_id IS NULL` 是反连接，典型用于“主表有、副本没有”。

- **🎙️ 考场直接背诵话术**：
  > 内连接只返回两边匹配上的行，结果范围是交集；左连接保留左表全部行，右表匹配不到就补 `NULL`；右连接反过来；全连接是两边都保留。MySQL 不直接支持 `FULL OUTER JOIN`，一般用左连接和右连接做 `UNION` 模拟。项目里查“已经关台但备份缺失”的记录，我会用 `order_table_fees LEFT JOIN core_backup`，然后过滤 `b.consumption_id IS NULL`，这能保留主表记录，同时找出没有副本的行；如果用内连接，缺失的记录反而被过滤掉了。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 内连接：交集
  SELECT o.order_id, d.consumption_id
  FROM orders o
  INNER JOIN order_product_consumptions d
    ON d.order_id = o.order_id;

  -- 左连接：保留左表，找右表缺失
  SELECT o.order_id
  FROM orders o
  LEFT JOIN order_product_consumptions d
    ON d.order_id = o.order_id
  WHERE d.order_id IS NULL;
  ```

## 📌 考点 18：ACID 四大特性

- **🗣️ 面试官原话汇总**：
  - 图7：“数据库的acid”
  - 图7：“讲讲事物的四大特性”

- **💡 30秒看懂本质（大白话版）**：  
  事务就像转账：A 扣钱和 B 加钱必须一起成功，不能只完成一半。ACID 是四个保证：

  - Atomicity 原子性：要么全做，要么全不做。
  - Consistency 一致性：事务前后，业务规则不能被破坏。
  - Isolation 隔离性：并发事务之间不要互相看到半成品。
  - Durability 持久性：提交成功后，即使断电也不能丢。

  InnoDB 里，原子性靠 undo log 回滚，持久性靠 redo log，隔离性靠 MVCC 和锁，一致性是业务约束 + 数据库约束共同保证的结果。

- **🔗 结合我的项目怎么讲**：

  建订单时，`orders` 主表、订单明细和待结算消费清扫在同一个事务里。任何一步失败就回滚，不能留下“订单建了但消费没清”或“消费清了但订单没建”的中间状态。关台/收款/库存则用条件更新保证状态不会被覆盖。

- **🎙️ 考场直接背诵话术**：
  > ACID 是原子性、一致性、隔离性、持久性。原子性保证一组操作要么全成功要么全失败，InnoDB 主要靠 undo log 回滚；持久性保证提交后的数据不因为崩溃丢失，主要靠 redo log；隔离性处理并发事务之间的可见性，靠 MVCC 和锁；一致性是最终目标，既包括数据库约束，也包括业务规则。我的项目里建订单会把订单主表、订单明细和待结算消费的删除放在同一个事务里，任何一步返回错误或抛异常都回滚。关台、收款和扣库存则用条件更新，防止状态被重复覆盖。

- **💻 核心代码/SQL 速记**：

  ```sql
  START TRANSACTION;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO order_product_consumptions (...) VALUES (...);
  DELETE FROM ongoing_product_consumptions WHERE consumption_id = ...;
  COMMIT;
  -- 任一步失败：ROLLBACK;
  ```

## 📌 考点 19：MySQL 隔离级别与 RR/RC

- **🗣️ 面试官原话汇总**：
  - 图4：“Mysql隔离级别”
  - 图6：“MySQL的事务隔离级别，可重复读怎么解决脏读”
  - 图7：“Mysql的RR和RC隔离级别”

- **💡 30秒看懂本质（大白话版）**：  
  隔离级别就是“并发事务之间能偷看到多少东西”。从松到严：

  1. 读未提交（READ UNCOMMITTED）：别人还没提交的改动也能看到，最容易脏读。
  2. 读已提交（READ COMMITTED）：只看到别人已提交的；但同一事务里两次查询可能看到不同结果（不可重复读）。
  3. 可重复读（REPEATABLE READ）：同一事务里普通查询看到同一份快照；MySQL InnoDB 默认级别。
  4. 串行化（SERIALIZABLE）：最严格，代价也最大。

  脏读是读到了别人未提交的数据；不可重复读是同一行两次读结果变了；幻读是同一范围两次读，行数变了。InnoDB 的 RR 通过 MVCC 提供一致性读，并用 next-key lock 处理当前读/范围锁，减少幻读。

- **🔗 结合我的项目怎么讲**：

  - 订单、支付、库存是钱和资源，不能读未提交。
  - 项目使用 MySQL 默认的 RR 作为基础；开台用 `FOR UPDATE` 是当前读，不是普通快照读。
  - 关台、收款、扣库存的条件更新本身就是当前读 + 行锁，保证后到请求看到最新状态。
  - 如果降到 RC，可能降低某些间隙锁带来的并发成本，但会增加不可重复读和幻读风险；这个系统没有必须降级的理由，所以不为了“看起来高并发”乱改。

- **🎙️ 考场直接背诵话术**：
  > MySQL 有四个隔离级别。读未提交会脏读；读已提交只读已提交数据，但同一事务里两次查询可能不一致；可重复读是 InnoDB 默认，通过 MVCC 给普通查询一个事务级快照，所以不会读到未提交数据；串行化最严格但并发度最低。RR 解决脏读不是靠“锁住整张表”，而是普通一致性读只读取创建 read view 时可见的已提交版本。项目里库存、桌台状态和支付状态不能被脏读，所以我不会用读未提交；开台和条件更新属于当前读，会看到最新已提交数据并加锁。

- **💻 核心代码/SQL 速记**：

  ```sql
  SELECT @@transaction_isolation;

  -- 只建议在明确知道影响的会话里切换
  SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
  ```

## 📌 考点 21：MVCC 是怎么实现的

- **🗣️ 面试官原话汇总**：
  - 图7：“MVCC怎么实现的”
  - 图6：“可重复读怎么解决脏读”

- **💡 30秒看懂本质（大白话版）**：  
  MVCC 像文档的“历史版本”。每行数据除了当前值，还保留它以前被谁改过、怎么找回旧版本的信息。你开始一个事务时拿到一张“可见版本清单”（read view），之后普通查询就按这张清单挑一个你能看到的版本，而不是直接看别人正在改的当前值。  
  这样读和写可以少打架：读的人看快照，写的人改当前行。它不是“没有锁”，而是普通一致性读尽量不靠锁。

- **🔗 结合我的项目怎么讲**：

  - 普通 `SELECT` 读待结算列表：在 RR 下可能读到事务开始时的快照。
  - 开台关键判断不能用普通快照读，否则可能看到旧状态；代码用 `SELECT ... FOR UPDATE` 做当前读，拿最新版本并加锁。
  - 关台、收款、库存扣减是 `UPDATE ... WHERE 条件`，属于当前读，不会拿旧快照去覆盖新状态。
  - 所以“MVCC 解决读并发”不等于“关键写路径可以不用锁”。

- **🎙️ 考场直接背诵话术**：
  > InnoDB 的 MVCC 主要靠隐藏事务版本、undo log 版本链和 read view。每行有事务 ID 和指向 undo 的指针，修改旧值会形成版本链；事务做普通查询时，根据 read view 判断哪些版本可见。RC 通常每条语句生成新的 read view，所以同一事务两次查询可能不同；RR 通常在事务第一次一致性读时生成一次，所以之后的普通读可重复。要注意 MVCC 主要服务一致性读，当前读比如 `SELECT ... FOR UPDATE` 和 `UPDATE` 还是要读最新版本并加锁。我的开台流程就是用当前读，不会用普通快照读来判断桌子是否空闲。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 普通快照读（MVCC）
  SELECT * FROM billiards_tables WHERE id = '3';

  -- 当前读 + 排他行锁（关键判断）
  SELECT * FROM billiards_tables WHERE id = '3' FOR UPDATE;
  ```

## 📌 考点 22：MySQL 有哪些锁，间隙锁和临键锁是什么

- **🗣️ 面试官原话汇总**：
  - 图6：“除了行锁这种排他锁之外，MySQL还有哪些锁，间隙锁和临键锁”
  - 图8：“了解过哪几种锁？”

- **💡 30秒看懂本质（大白话版）**：  
  把索引想象成一排座位：

  - 记录锁：锁住某一个具体座位。
  - 间隙锁：锁住两个座位之间的空位，防止别人往这里塞新记录。
  - 临键锁：锁住“座位 + 前面的空位”，也就是记录锁加间隙锁。
  - 表锁/意向锁：更大范围的锁；意向锁是“我准备锁某几行”的标记，减少表锁和行锁互相判断的成本。

  InnoDB 的行锁是加在索引上的；如果查询条件没有走索引，可能退化成大范围扫描和更多锁，代价很高。

- **🔗 结合我的项目怎么讲**：

  - 开台锁的是 `billiards_tables` 的一行，条件走主键 `id`，锁范围比较明确。
  - 关台、收款、扣库存的 `UPDATE` 也尽量走主键，避免无索引条件扩大锁范围。
  - `outbox_events` 用 `FOR UPDATE SKIP LOCKED` 领取事件，允许多个 worker 跳过已被锁住的行；这是“行锁 + 跳过已锁行”的工程用法。
  - 当前项目没有专门测试间隙锁和死锁；面试时可以说“机制上理解，项目里通过主键和短事务降低风险”，不要硬说做过死锁演练。

- **🎙️ 考场直接背诵话术**：
  > InnoDB 常见锁可以按粒度和模式分。粒度上有表锁、行锁、间隙锁、临键锁和意向锁；模式上有共享锁和排他锁。记录锁锁具体索引记录，间隙锁锁索引记录之间的空隙，临键锁是记录锁加间隙锁，主要用于 RR 下减少幻读。关键点是 InnoDB 行锁落在索引上，所以条件能不能走索引会影响锁范围。项目里开台按主键锁桌台行，关台、收款和库存按主键做条件更新；outbox worker 用 `FOR UPDATE SKIP LOCKED` 领取未锁事件，避免多个 worker 抢同一行。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 共享锁：允许别人也读，阻塞别人改
  SELECT * FROM products WHERE id = 'P_001' FOR SHARE;

  -- 排他锁：我准备改，别人读写都要等
  SELECT * FROM products WHERE id = 'P_001' FOR UPDATE;

  -- 多 worker 领取任务，跳过已被锁住的行
  SELECT event_id FROM outbox_events
  WHERE status = 'pending'
  ORDER BY event_id
  LIMIT 20
  FOR UPDATE SKIP LOCKED;
  ```

## 📌 考点 23：库存扣减的共享锁 SQL 怎么写

- **🗣️ 面试官原话汇总**：
  - 图6：“库存扣减，对某一行数据加共享锁，你知道怎么写sql语句”

- **💡 30秒看懂本质（大白话版）**：  
  共享锁像“几个人可以同时看同一本书，但谁都不能改”。SQL 是 `SELECT ... FOR SHARE`（旧写法 `LOCK IN SHARE MODE`）。  
  但库存扣减如果先用共享锁查、再改成排他锁更新，多个事务可能同时拿着共享锁，然后都想升级成排他锁，容易互相等待甚至死锁。更稳的是直接用排他锁，或者更好：**把判断和扣减合成一条带条件的 `UPDATE`**。

- **🔗 结合我的项目怎么讲**：

  当前项目扣库存用的是原子条件更新：

  ```sql
  UPDATE products
  SET 库存 = 库存 - %s
  WHERE id = %s AND 库存 >= %s;
  ```

  它会锁住目标行，并在同一句里完成“判断库存够不够 + 扣减”。如果 `rowcount=0`，再查一次区分商品不存在和库存不足。  
  如果面试官明确问“共享锁怎么写”，先给：

  ```sql
  SELECT id, 库存
  FROM products
  WHERE id = %s
  FOR SHARE;
  ```

  然后补充：“共享锁适合只读校验，不适合作为库存扣减的最终方案。”

- **🎙️ 考场直接背诵话术**：
  > 共享锁的 SQL 是 `SELECT ... FOR SHARE`，MySQL 8 也兼容旧写法 `LOCK IN SHARE MODE`。它允许多个事务同时读同一行，但阻塞排他锁。库存扣减我会说明：如果只是查询展示，共享锁可以；但如果查完还要扣，我不推荐先拿共享锁再升级，因为可能有锁升级和死锁风险。项目里我直接用 `UPDATE products SET 库存 = 库存 - ? WHERE id = ? AND 库存 >= ?`，让数据库在同一句里做当前读、行锁和条件判断，命中 0 行再查原因。这样既不超卖，也少一次往返。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 题目问共享锁时这样写
  SELECT id, 库存
  FROM products
  WHERE id = %s
  FOR SHARE;

  -- 真正扣库存推荐
  UPDATE products
  SET 库存 = 库存 - %s
  WHERE id = %s
    AND 库存 >= %s;
  ```

## 📌 考点 24：悲观锁、乐观锁，项目用哪种

- **🗣️ 面试官原话汇总**：
  - 图8：“乐观锁的实现方案有哪些？”
  - 图8：“项目中用什么关键字加锁？”
  - 图6：“库存扣减，对某一行数据加共享锁，你知道怎么写sql语句”

- **💡 30秒看懂本质（大白话版）**：  

  - 悲观锁：我先假设一定会有人抢，所以先锁住，别人等着。数据库里常见 `SELECT ... FOR UPDATE`，或者直接 `UPDATE` 拿排他锁。
  - 乐观锁：我先不锁，更新时检查“版本号/旧值有没有变”；变了就说明被人改过，重试或报错。常见 `WHERE version = 旧版本`。

  两者不是谁高级，而是冲突概率和重试成本的取舍。

- **🔗 结合我的项目怎么讲**：

  - 开台：用悲观行锁 `SELECT ... FOR UPDATE`，因为抢同一张桌是低频但必须正确的冲突。
  - 关台/收款/库存：用条件更新，本质是让数据库做当前读和行锁；库存 `WHERE 库存 >= 数量` 也可以看作一种“带业务条件的乐观并发控制”，但我会谨慎地称它为“条件更新”，不硬贴乐观锁标签。
  - 如果以后做商品编辑，可以加 `version` 字段做乐观锁，避免两个店员互相覆盖价格。
  - Python 里 `threading.Lock` 只能保护单进程内的线程，不能替代数据库锁；多进程/多实例下真正的事实源还是 MySQL。

- **🎙️ 考场直接背诵话术**：
  > 悲观锁是预先锁住资源，适合冲突概率高、冲突代价大的场景，数据库里典型是 `SELECT ... FOR UPDATE`；乐观锁是先读版本，更新时用 `WHERE version = old_version` 检查有没有被别人改过，失败就重试或提示用户。项目里开台用悲观锁，因为两个人同时抢同一张桌，必须让后到的人等锁后看到最新状态；关台、收款、扣库存用条件更新，把状态条件写进 `UPDATE`，避免应用层先查再写。Python 进程内的 `Lock` 只能保护线程，不跨进程，所以我的跨请求正确性不依赖它。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 悲观锁
  SELECT id FROM products WHERE id = %s FOR UPDATE;

  -- 乐观锁
  UPDATE products
  SET 库存 = 库存 - %s, version = version + 1
  WHERE id = %s
    AND 库存 >= %s
    AND version = %s;
  ```

  ```python
  # 进程内锁：只保护单进程线程，不替代数据库锁
  import threading
  lock = threading.Lock()
  with lock:
      ...
  ```

## 📌 考点 25：MySQL 死锁场景与避免

- **🗣️ 面试官原话汇总**：
  - 图4：“Mysql死锁场景”

- **💡 30秒看懂本质（大白话版）**：  
  死锁就是两个人各拿一把钥匙，又都等对方手里的钥匙，谁也不肯先放。数据库里常见的是两个事务以相反顺序锁两行：

  ```text
  事务 A：锁第 1 行 → 想锁第 2 行
  事务 B：锁第 2 行 → 想锁第 1 行
  ```

  InnoDB 会检测等待环，通常回滚其中一个事务，让另一个继续。应用层要能识别死锁并重试。

- **🔗 结合我的项目怎么讲**：

  - 开台先锁 `billiards_tables` 的单行，再写台位费/明细，锁顺序比较固定。
  - 关台、收款、库存更新都尽量走主键，缩小锁范围。
  - 事务里不做网络请求、不等待用户输入、不长时间计算。
  - 如果未来一个事务要锁多张表，按固定顺序锁；不要在事务中间再去拿另一把锁。
  - 当前项目没有专门做死锁注入演练，面试时不要编“我遇到过并解决了线上死锁”；可以讲你如何设计来降低概率。

- **🎙️ 考场直接背诵话术**：
  > 死锁的典型场景是两个事务以相反顺序争用多把锁，或者一个事务持有共享锁后想升级排他锁，另一个事务也在等它。InnoDB 会检测死锁并回滚其中一个事务，业务层要做的是缩短事务、固定加锁顺序、让条件走索引、减少锁范围，并对可重试的死锁做有限次退避重试。项目里开台只锁一张桌子的主键行，之后的写操作按固定顺序执行；关台、收款、库存用主键条件更新。我的目标不是承诺永远没有死锁，而是让锁范围小、顺序稳定、失败可恢复。

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 固定顺序：先锁 A，再锁 B；所有事务都遵守
  SELECT * FROM resource_a WHERE id = %s FOR UPDATE;
  SELECT * FROM resource_b WHERE id = %s FOR UPDATE;
  ```

  ```python
  # 对可重试死锁做有限次退避，不要无限重试
  for attempt in range(3):
      try:
          return do_transaction()
      except DeadlockError:
          if attempt == 2:
              raise
          time.sleep(0.05 * (2 ** attempt))
  ```

## 📌 考点 26：怎么避免事务冲突

- **🗣️ 面试官原话汇总**：
  - 图7：“怎么避免事物冲突的”
  - 图7：“讲讲事物的四大特性”

- **💡 30秒看懂本质（大白话版）**：  
  减少冲突不是“把数据库锁全加上”，而是让事务更短、锁更小、顺序更稳定、条件更精确。就像路口堵车，不是把整条路封起来，而是缩短占用时间、统一通行方向、减少无效车辆。

- **🔗 结合我的项目怎么讲**：

  - 开台事务只锁目标桌台行，不锁全表。
  - 事务内不做耗时网络调用，不等待用户确认。
  - 关键状态转换用条件更新，避免“读到旧状态再写回”。
  - 订单创建把主表、明细、待结算清扫放在同一事务，保证边界完整。
  - 读多的展示路径和写路径分开，避免长事务。
  - 热点库存行会有竞争，但单店规模下优先正确性；如果未来高并发，再考虑分桶库存、队列串行化等方案，而不是现在盲目上 Redis。

- **🎙️ 考场直接背诵话术**：
  > 我会从四个方向降低事务冲突：第一，缩短事务，把网络请求、文件写入和用户等待移出事务；第二，缩小锁范围，条件尽量走主键或合适索引，不做无索引的大范围更新；第三，固定多行/多表的加锁顺序，降低循环等待；第四，能用一个带条件的 `UPDATE` 完成判断和写入，就不在应用层先查再写。项目里开台锁单张桌，订单相关写操作放在同一个短事务里，库存用 `库存 >= 数量` 的条件更新。高并发时还要配合重试、监控和压测，不能只靠一句“加锁”解决。

- **💻 核心代码/SQL 速记**：

  ```text
  短事务 → 小锁范围 → 固定顺序 → 精确条件 → 有限重试 → 监控
  ```

## 📌 考点 27：SQL 注入怎么防

- **🗣️ 面试官原话汇总**：
  - 图4：“SQL注入”

- **💡 30秒看懂本质（大白话版）**：  
  SQL 注入就像你把用户输入的“名字”直接拼进一张表格的指令里，用户输入 `' OR 1=1 --`，数据库可能把后半句当成命令执行。防法的核心不是“过滤几个关键字”，而是**把 SQL 结构和用户数据分开**：用参数化查询，让驱动负责转义/绑定；动态表名/列名用白名单。

- **🔗 结合我的项目怎么讲**：

  - 代码里使用 PyMySQL 的 `%s` 占位符，不把用户输入拼进 SQL 字符串。
  - 请求参数用 Pydantic 校验类型和范围。
  - 数据库账号按最小权限，不让应用账号拥有建库、删库、改权限等能力。
  - 动态排序字段不能直接拼接，要映射到白名单。
  - 错误响应不要暴露 SQL、表名和堆栈给外部。

- **🎙️ 考场直接背诵话术**：
  > 防 SQL 注入最核心的是参数化查询，不是靠手写正则过滤。比如 Python 里用 PyMySQL 的 `cursor.execute(sql, params)`，SQL 里用 `%s` 占位，驱动会把参数当成数据绑定，而不是把输入拼成 SQL 语法。动态表名、列名、排序方向不能用参数占位符解决，所以我会用白名单映射。项目里同时用 Pydantic 做类型校验、数据库账号最小权限、统一错误响应，避免把 SQL 和堆栈泄露出去。只要是有用户输入的查询，我都不会用字符串拼接。

## 📌 考点 28：重复开台、重复关台、重复收款、库存超卖怎么防

- **🗣️ 面试官原话汇总**：
  - 图6：“库存扣减，对某一行数据加共享锁，你知道怎么写sql语句”
  - 图6：“缓存商品信息，库存也要放在里面，库存怎么防止超卖？”
  - 图8：“项目中用什么关键字加锁？”
  - 这是项目真实代码对应的核心追问。

- **💡 30秒看懂本质（大白话版）**：  
  不要相信“先查一下再写”的应用逻辑，因为两个请求可能同时查到“可以”，然后都写。正确做法是让数据库在**同一条语句里**完成“条件判断 + 修改”，或者用事务锁把关键判断串行化。  
  幂等不是“重复请求都返回成功”，而是“同一个业务动作执行多次，结果和副作用不重复”。

- **🔗 结合我的项目怎么讲**：

  | 场景 | 关键条件 | 代码/思路 |
  |---|---|---|
  | 重复开台 | 先锁桌台行，再在事务内查无未关台台位费 | `SELECT ... FOR UPDATE` + 二次检查 |
  | 重复关台 | `关台时间 IS NULL` | `UPDATE ... WHERE consumption_id=? AND 关台时间 IS NULL` |
  | 重复收款 | `支付状态 = '未支付'` | `UPDATE ... WHERE order_id=? AND 支付状态='未支付'` |
  | 超卖 | `库存 >= 数量` | `UPDATE ... SET 库存=库存-? WHERE id=? AND 库存>=?` |
  | 重复备份 | `consumption_id` 唯一/幂等写入 | 重复处理不产生重复行 |

  还要讲 `rowcount == 0` 的处理：不要直接说“成功”，而是再查一次，区分记录不存在、状态已变化、库存不足，返回明确错误。

- **🎙️ 考场直接背诵话术**：
  > 我的原则是把关键条件放进数据库，而不是在 Python 里先查再写。开台时用 `SELECT ... FOR UPDATE` 锁住桌台行，并在事务内重新读取待结算消费，确认没有未关台记录才插入；关台用 `关台时间 IS NULL`，收款用 `支付状态 = '未支付'`，扣库存用 `库存 >= 数量`。如果更新影响行数为 0，我会再查一次，区分“记录不存在”和“状态已经被别人改过”。这既是并发控制，也是业务幂等的一部分。需要说明的是，我目前没有实现一个通用的幂等 Token 中间件；项目里落地的是条件更新、状态机、唯一约束/主键和 outbox 的幂等写入。Redis Token 和 `action_id` 是我下一步的设计。

## 📌 考点 29：数据库连接池怎么讲，参数怎么定

- **🗣️ 面试官原话汇总**：
  - 图9：“线程池有几种创建方式，四大拒绝策略……核心线程数和最大线程数……”
  - 这题原题问的是 Java 线程池；数据库连接池是项目里的加分对照，不是原题。

- **💡 30秒看懂本质（大白话版）**：  
  线程池是“复用工人”，连接池是“复用通往数据库的电话线”。每次请求都新建 MySQL 连接，就像每打一次电话都重新拉一根线，握手和认证很贵。连接池预先准备几条可复用连接，借出、归还、限制最大并发。  
  连接池参数不是越大越好：数据库总连接数有限，池开太大只会把压力推给 MySQL，造成排队、内存和上下文切换。

- **🔗 结合我的项目怎么讲**：

  - `backend/io_layer.py` 用 DBUtils `PooledDB`，主库 `maxconnections=10`、`mincached=2`、`maxcached=10`，备份库独立池 `maxconnections=5`。
  - `blocking=True`：池满时等待，而不是直接失败。
  - `ping=1`：借出时检查连接可用性，减少拿到死连接。
  - `reset=True`：归还时重置会话状态，避免上一个调用方的事务/会话污染下一个。
  - 备份库使用独立池，避免主库连接被备份任务占用。
  - 压测结果：同机 10 并发、200 请求，p50 约 432ms → 约 28ms，p95 约 530–575ms → 约 44ms；这只是本机合成压测，不是线上 SLA。

- **🎙️ 考场直接背诵话术**：
  > 连接池的核心是复用连接、限制并发和保护数据库。参数上，`maxconnections` 是池的上限，`mincached` 是预热保底，`maxcached` 是空闲缓存上限，`blocking` 决定池满时等待还是报错，`ping` 和 `reset` 分别处理连接存活和会话清理。我的项目主库最大 10 条连接，备份库单独 5 条，避免备份写库挤占主业务连接。压测时我发现瓶颈不是 SQL，而是每次请求新建连接；引入 DBUtils 后，同机 10 并发、200 请求的 p50 从约 432ms 降到约 28ms。但我会强调这是本机合成压测，真实生产还要看数据库上限、请求模型和部署形态。

- **💻 核心代码/SQL 速记**：

  ```python
  PooledDB(
      creator=pymysql,
      maxconnections=10,
      mincached=2,
      maxcached=10,
      blocking=True,
      ping=1,
      reset=True,
      **DB_CONFIG,
  )
  ```

- **💻 核心代码/SQL 速记**：

  ```sql
  -- 1. 查某张桌当前未关台的台位费
  SELECT consumption_id, 开台时间, 每小时价格
  FROM ongoing_table_fees
  WHERE 桌台编号 = %s
    AND 关台时间 IS NULL;

  -- 2. 查订单主表 + 商品明细
  SELECT o.order_id, o.桌台编号, o.总金额,
         d.商品名称, d.数量, d.金额
  FROM orders o
  INNER JOIN order_product_consumptions d
    ON d.order_id = o.order_id
  WHERE o.order_id = %s;

  -- 3. 找缺失的核心备份（主表有、备份没有）
  SELECT f.consumption_id
  FROM order_table_fees f
  LEFT JOIN core_backup b
    ON b.consumption_id = f.consumption_id
  WHERE b.consumption_id IS NULL;

  -- 4. 按桌台统计已支付订单金额
  SELECT 桌台编号, SUM(总金额) AS 实收金额
  FROM orders
  WHERE 支付状态 = '已支付'
  GROUP BY 桌台编号
  HAVING SUM(总金额) > 0
  ORDER BY 实收金额 DESC;

  -- 5. 两表所有 id（保留重复）
  SELECT consumption_id AS id FROM ongoing_table_fees
  UNION ALL
  SELECT consumption_id AS id FROM order_table_fees;

  -- 6. 每个桌台最近一笔订单（MySQL 8 窗口函数）
  SELECT *
  FROM (
      SELECT o.*,
             ROW_NUMBER() OVER (
                 PARTITION BY 桌台编号
                 ORDER BY 创建时间 DESC
             ) AS rn
      FROM orders o
  ) t
  WHERE rn = 1;

  -- 7. 安全扣库存
  UPDATE products
  SET 库存 = 库存 - %s
  WHERE id = %s
    AND 库存 >= %s;
  ```

## 📌 考点 31：金额为什么用 DECIMAL，不用 float

- **🗣️ 面试官原话汇总**：
  - 图7：“讲一下浮点数怎么判断相等；计算机浮点数怎么实现的；给定两个1.3，他们一定相等吗”
  - 这是从浮点数题自然延伸到项目金额设计。

- **💡 30秒看懂本质（大白话版）**：  
  十进制小数 `1.3` 在二进制里往往不能精确表示，就像用只能写三等分的尺子量 1/3，总会有近似误差。金额如果经过 `float`，可能出现 `59.999999`，再截断就变成 59。  
  金额应该用十进制类型：数据库 `DECIMAL`，Python `Decimal`，序列化时明确输出字符串或约定格式。

- **🔗 结合我的项目怎么讲**：

  - 表里金额列是 `DECIMAL(10,2)`。
  - 后端读取后保持 `Decimal`，不经过 `float`。
  - 台费按秒计算，再按业务规则取整；商品小计和订单合计保留两位。
  - HTTP JSON 出口把 `Decimal` 转成字符串，避免标准库不能序列化 `Decimal`，也避免在边界又退回二进制浮点。
  - 前端只展示后端金额，不重新计算台费/订单金额。

- **🎙️ 考场直接背诵话术**：
  > 二进制浮点数不能精确表示很多十进制小数，所以直接用 `float` 比较金额会不稳定，正确做法是比较误差范围，金额业务则更应该用 `Decimal` 或数据库 `DECIMAL`。我的项目里数据库金额列是 `DECIMAL(10,2)`，Python 后端读出来保持 `Decimal`，台费按秒精确计算，商品小计和订单合计按业务规则保留两位；JSON 出口把 `Decimal` 转成字符串。前端只展示后端返回值，不自己算钱。这样避免“59.999999 被截成 59”这种问题。

- **💻 核心代码/SQL 速记**：

  ```python
  from decimal import Decimal, ROUND_HALF_UP

  price = Decimal("3.00")
  quantity = Decimal("2")
  amount = (price * quantity).quantize(
      Decimal("0.01"),
      rounding=ROUND_HALF_UP
  )
  ```
