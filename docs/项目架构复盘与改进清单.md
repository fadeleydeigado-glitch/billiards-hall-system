## 1. 项目现在到底完成了什么

### 1.1 系统结构

当前请求路径可以概括为：

```text
浏览器
  └─ Vue 3 页面 + 原生 ES Modules
       └─ FastAPI 路由（api_layer.py）
            └─ 控制层（controller_layer.py）：流程编排、事务边界
                 └─ 业务层（business_layer.py）：检查、计算、组装数据
                      └─ IO 层（io_layer.py）：MySQL、事务、日志
                           └─ MySQL 8.x：11 张表
```

函数前缀与职责：

| 前缀 | 所在层 | 当前职责 | 需要强调的边界 |
|---|---|---|---|
| `api_*` | API 层 | 接收 HTTP 参数，转交控制层 | 目前只做参数转交，没有独立请求模型和 HTTP 错误映射 |
| `three_*` | 控制层 | 组织业务流程，决定事务边界，写业务日志 | 结账不是跨“关台—建单—收款”的一个大事务 |
| `two_*` | 业务层 | 结构检查、业务判断、金额组装 | 目前仍有两个 IO 依赖，不能称为“完全纯函数” |
| `one_*` | IO 层 | 连接 MySQL、执行 SQL、管理事务、写日志 | 事务函数接收外部 cursor 时，自己不会提交事务 |

### 1.2 已实现的五条核心写路径

| 流程 | 事务内保证 | 并发或重复请求保护 | 失败时的行为 |
|---|---|---|---|
| 开台 | 锁桌台配置行、重新读取待结算消费、插入台位费 | `SELECT ... FOR UPDATE` + 事务内二次检查 | 已被占用则返回 `TableOccupied`，不写入 |
| 加商品 | 插入商品消费、扣库存 | 扣库存使用 `库存 >= 数量` 条件更新 | 任一写入失败，整个事务回滚 |
| 关台 | 写关台时间和台费金额 | `关台时间 IS NULL` 条件更新 | 重复关台被数据库行状态拦截 |
| 建订单 | 插订单、插明细、删除待结算消费 | 删除待结算记录时检查命中行数 | 任一步失败，订单和消费清扫一起回滚 |
| 收款 | 把订单从“未支付”改为“已支付” | `支付状态 = '未支付'` 条件更新 | 重复收款被状态条件拦截 |

这张表比“用了 MySQL、FastAPI、Vue 3”更能说明项目质量。真正的工程价值在于：**每一步都知道谁会读这个结果，以及失败后应该留下什么状态。**

### 1.3 开台并发保护

开台不是简单执行一条 `INSERT`。当前实现是：

1. 事务外先做一次读取和提示；
2. 进入事务后锁住 `billiards_tables` 中对应桌台行；
3. 用事务内的 cursor 重新读取该桌待结算消费；
4. 再次确认桌子空闲；
5. 才插入台位费记录。

对应代码：`backend/controller_layer.py:400-473`，行锁函数在 `backend/io_layer.py:1043-1087`。

这解决的是“两个前台同时开同一张桌”的写冲突，不等于系统已经通过高并发压力测试。

### 1.4 条件更新与事务回滚

以下保护都属于数据库层的状态守卫：

- 关台：`WHERE consumption_id = %s AND 关台时间 IS NULL`
- 收款：`WHERE order_id = %s AND 支付状态 = '未支付'`
- 扣库存：`WHERE id = %s AND 库存 >= %s`
- 事务封装：`backend/io_layer.py:940-987`

它们的作用是：即使两个请求同时到达，也不会让同一个台位重复关台、同一张订单重复收款，或把库存扣成负数。

## 2. 外部评审中“成立”的部分

### 2.1 从 JSON 到 MySQL 的迁移是实质性重构

不是简单把文件读写换成 SQL，而是重新定义了：

- 事实源：桌台状态、订单、库存、支付状态进入 MySQL；
- 写路径：事务边界集中到控制层；
- 失败处理：数据库报错被转换为统一的结果字典；
- 测试方式：从手工点击变成可重复的脚本验证。

### 2.2 测试不是“摆样子”

项目中有三层验证：

1. `tests/test_mysql_write.py`
   - 把 10 个低层写函数放在同一个事务中执行；
   - 每步执行后在同一事务内查询验算；
   - 最后统一 `rollback()`；
   - 用新连接做前后快照比对，确认没有留下脏数据。

2. `tests/test_full_flow.py`
   - 覆盖完整用户故事、10 个错误分支和 1 个事务回滚场景；
   - 在 `run_rollback_test()` 中临时替换扣库存函数，构造“商品消费已插入，但扣库存失败”的故障；
   - 用 `finally` 还原原函数，并用 `is` 检查函数对象是否恢复；
   - 日志中能看到模拟失败记录。

3. `scripts/check_data.py`
   - 检查待结算主表与明细表行数；
   - 检查 `S_` 记录的创建时间是否被错误写成同桌台开台时间；
   - 检查孤儿记录和金额；
   - 对订单表执行附加一致性检查。

这些测试说明项目已经开始用“可重复证据”代替“我觉得应该没问题”。

### 2.3 归档和配置管理是成熟做法

- Git 标签 `pre-cleanup-2026-11-05` 保留旧版本快照；
- `archive/legacy-json/` 和 `archive/native-frontend/` 隔离旧实现；
- `.gitignore` 排除了 `.env`、日志和缓存；
- `.env.example` 只保留配置模板；
- 业务日志与 Uvicorn 日志离开代码目录。

这部分可以准确表述为“有版本回退意识和配置隔离意识”，不必夸成“大厂标准”，但确实比多数个人项目更完整。

### 2.4 两篇设计文档是有价值的资产

`docs/设计思路总结.md` 的核心判断是：

> 结果会被下一步读到、或客人当场必须看到，就放在主路径；否则才放旁路，并准备补偿。

这个判断标准可以解释为什么库存、桌台状态和支付状态不能随便异步化。`docs/AI_EMPLOYEE.md` 则把 AI 放在控制层之外，要求工具调用白名单、代码算钱、两阶段确认和幂等键。

但要区分：

- **设计判断成立**：文档里的边界分析有价值；
- **功能尚未实现**：当前仓库并没有 `ai/` 目录、`policy_engine.py` 或工具注册表。

## 3. 需要修正的说法

外部评审里有几处表达方向正确，但结论说过头了。建议统一改成下面的口径。

### 3.1 “工业级全栈架构”

不建议直接这样写。更准确的说法是：

> **面向生产约束设计的单店全栈项目：核心写路径已经具备事务、幂等和失败回滚意识；尚未补齐认证、外部 API 契约、监控、独立备份和部署验证。**

“有生产意识”与“已达到生产级”是两件事。

### 3.2 “支持高并发”

当前能证明的是：

- 开台写冲突有行锁保护；
- 关台、收款、扣库存有条件更新；
- 事务回滚测试通过。

当前不能证明的是：

- 系统吞吐量；
- 多进程或多实例下的行为；
- 长时间运行后的锁等待、死锁和连接池表现；
- 前后端并发刷新时的数据一致性。

所以应写成“**关键写冲突有数据库级并发保护**”，不要写成“支持高并发”。

### 3.3 “SaaS 系统”

当前没有：

- 登录、角色和权限；
- 多租户字段；
- 租户级数据隔离；
- 真实支付回调；
- 公网部署和安全边界。

更准确的说法是“单店部署的全栈业务系统”。未来可以演进为 SaaS，但现在还不是。

### 3.4 “AI 员工已经落地”

准确说法：

> **AI 员工完成了目标架构和落地路线设计，尚未进入代码实现阶段。**

目前有设计文档，没有可调用的 AI 工具、规则引擎、会话状态和评测集。

### 3.5 “9 条标准 RESTful 路由”

`backend/api_layer.py` 确实有 9 条业务路由：

```text
GET  /frontend/refresh
GET  /frontend/products
GET  /frontend/unpaid-orders
GET  /tables/checkout-options
POST /tables/open
POST /tables/close
POST /orders/unpaid
POST /payments/confirm
POST /products/consumption
```

但它们是“9 条业务 HTTP 接口”，更接近 RPC 风格，不是完整的 REST 资源模型：

- 请求体大量直接使用 `dict`，没有 Pydantic 模型；
- 业务错误通常仍返回 HTTP 200；
- 错误信息放在 `status / error_type / message` 中，由前端自己判断。

这对当前同源前端是可用的，但对接 AI 工具、第三方客户端或网关时，需要重新定义契约。

### 3.6 “日志和备份是异步旁路”

更准确的说法：

- **业务日志**：在业务操作返回前同步调用，写文件失败只打印提示，不阻断主流程；它是“失败隔离”，不是“异步队列”。
- **核心备份**：关台事务提交成功后，另开一个事务尝试写入；备份失败不回滚关台，但也没有自动补偿任务。

因此目前应称为“可失败的旁路动作”，不能称为“已经实现最终一致补偿”。

### 3.7 “双驱动是完全冗余”

这个判断只对了一半：

- 主后端和 Python 测试使用 `PyMySQL`；
- `scripts/views/`、归档迁移脚本使用 `mysql-connector-python`；
- `check_data.py` 会优先使用 connector，失败再回退到 PyMySQL。

所以它不是“同一个业务连接同时用两个驱动”的正确性 bug，而是“不同运行面使用了不同驱动”的依赖复杂度。可以收敛，但不值得当成架构级错误。

### 3.8 日志里的“缺少订单编号”

`logs/business.log` 中确实有：

```text
[2026-11-06 00:06:10] [人] [确认收款] [订单=?] [失败：前端支付数据缺少订单编号]
```

但这条日志只能证明：

1. 后端正确拦截了一个缺少 `订单编号` 的请求；
2. 该请求到达了收款接口。

它不能直接证明 Vue 页面正常操作时漏传了订单号。`frontend/app.js:562-571` 在提交前会检查 `selectedOrder`，并读取 `selectedOrder.order_id`。要判断是否真的存在前端 bug，需要用页面操作复现请求体，或检查当时的网络请求。不能仅凭日志下结论。

### 3.9 “业务层已经完全剥离 IO”

这是当前最需要纠正的技术判断。

现状是：

- `backend/business_layer.py:3-6` 从 IO 层导入了 `one_get_current_time` 和 `one_insert_core_backup_to_mysql`；
- `two_backup_consumption_to_core_blackbox()` 会直接调用 IO 写函数；
- `two_create_unpaid_bill()` 会调用 `one_get_current_time()`。

因此业务层目前是“大部分是纯检查和计算，但仍有备份写入与时间获取的 IO 依赖”，不是“完全剥离 IO”。

这不是功能错误，但会影响：

- 业务函数的独立单元测试；
- 未来替换数据库或时间源；
- 对“业务层可以脱离基础设施运行”的架构承诺。

建议把备份写入上移到控制层，把当前时间作为参数传入 `two_create_unpaid_bill()`。验收标准是 `business_layer.py` 不再导入 `io_layer`，所有 `two_*` 函数都能在没有数据库连接时被测试。

## 4. 当前真正需要补的工程缺口

### P0：轮换已暴露的数据库凭据

**现状**

- 真实密码曾出现在外部对话中；
- `.env` 已被 `.gitignore` 忽略，且当前没有被 Git 跟踪；
- 这不代表密码没有泄露，只代表它没有进入当前仓库历史。

**为什么必须处理**

数据库密码一旦离开本机，就应该视为已泄露。即使当前是 `localhost`，也应避免继续使用同一个 root 密码。

**动作**

1. 修改 MySQL root 密码，或创建专用的应用账户；
2. 更新本机 `.env`；
3. 重启后端，确认旧密码失效、新密码可用；
4. 检查历史提交和外部聊天记录，避免再次复用；
5. 生产环境不要使用 root，给应用账户只授予所需库表的权限。

**验收**

- 旧密码无法连接；
- 新密码只存在于本机环境变量或本地 `.env`；
- `git log --all -- .env` 没有敏感文件历史；
- 文档、日志和代码中都不出现明文密码。

### P1：把业务层真正变成可独立测试的层

**现状**

`business_layer.py` 仍导入 IO 层函数，`two_backup_consumption_to_core_blackbox()` 负责实际写数据库。

**动作**

- 将“备份数据准备”留在业务层；
- 将“写 core_backup”移到控制层或 IO 层；
- 把当前时间由控制层作为参数传入；
- 让所有 `two_*` 函数只依赖输入参数和标准库。

**验收**

- `business_layer.py` 中不存在 `from .io_layer import ...`；
- 不启动 MySQL 也能导入并测试业务函数；
- 原有完整流程测试仍然通过。

### P1：给会写库的测试加环境闸门

**现状**

`tests/test_full_flow.py` 的说明明确写了“测试数据保留，不清理（测试库）”，但没有看到强制环境变量或数据库名白名单。只要连接配置指向真实库，脚本就可能写入真实数据。

**动作**

- 运行前要求显式设置 `ALLOW_WRITE_TESTS=1`；
- 要求 `MYSQL_DATABASE` 命中测试库白名单；
- 在写入前检查目标库不是生产库；
- README 中把“会写库”和“会回滚”分开说明。

**验收**

- 不设置许可变量时，脚本在连接数据库之前退出；
- 指向错误数据库时直接拒绝执行；
- 正常测试仍能覆盖完整流程。

### P1：补上备份缺口检查与幂等补录

**现状**

关台成功后才尝试写 `core_backup`。备份失败时，接口仍返回关台成功，并只在消息中说明。这是有意的“旁路失败不回滚”，但目前没有：

- 定期检查“已关台但备份缺失”的脚本；
- 幂等补录入口；
- 补录后的一致性验收标准。

另外，`one_insert_core_backup_to_mysql()` 是普通 `INSERT`。如果补录脚本重复执行，可能遇到主键重复，需要在补录脚本里显式忽略重复或改成幂等写法。

**动作**

1. 增加只读检查，分别检查仍在 `ongoing_table_fees` 的已关台记录和已经进入 `order_table_fees` 的记录；
2. 通过 `consumption_id` 关联 `core_backup`，找出缺失项；
3. 先 dry-run，再执行补录；
4. 补录按 `consumption_id` 去重，保证重复执行不产生副作用；
5. 保留执行记录。

**验收**

- 正常状态下缺口查询返回 0 行；
- 人为制造一次备份失败后，检查脚本能发现缺口；
- 补录后再次查询返回 0 行；
- 连续执行两次补录不会报主键冲突或产生重复数据。

### P1：明确 API 错误契约

**现状**

控制层返回四键字典，API 层直接返回给客户端；业务失败通常仍是 HTTP 200。当前前端会根据 `result.status` 展示错误，所以页面能用，但这不是清晰的 HTTP 契约。

**动作**

- 为请求体增加 Pydantic 模型；
- 为 `error_type` 建立稳定的错误码；
- 区分 400/404/409/422/500；
- 在 API 文档中声明成功和失败响应；
- 保持四键结果字典作为业务内部协议，或明确把它定义为对外协议。

**验收**

- 缺参数、资源不存在、状态冲突能被客户端按 HTTP 状态识别；
- 前端展示逻辑不依赖“200 + status=error”这一隐含约定；
- AI 工具层不需要猜测错误类型。

### P2：金额计算统一使用 `Decimal`

**现状**

`two_calculate_table_fee()` 先做浮点乘法，再用 `int()` 舍弃小数。当前规则明确是向下取整，但金额计算直接使用浮点数，在边界时长和两位小数价格上可能产生精度误差。

**动作**

- 用 `Decimal` 读取和计算金额；
- 明确取整规则，并写进测试；
- 对“刚好落在整数边界”的时长、价格为两位小数的场景增加断言。

**验收**

- 同样的输入在不同机器上得到相同结果；
- 不出现 `59.999999` 被截成 `59` 这类浮点边界问题；
- 取整规则在 README 和测试中一致。

### P2：收敛依赖和热重载范围

**现状**

- `requirements.txt` 同时安装 PyMySQL 和 mysql-connector-python；
- `check_data.py` 有双驱动回退，设计上合理；
- README 使用 `uvicorn ... --reload`，日志显示修改 `scripts/check_data.py` 会触发后端重启。

**动作**

- 保留主后端的 PyMySQL；
- 把只在历史脚本/查看工具中使用的 connector 放到可选依赖或运维依赖；
- 启动命令改为只监控后端目录，例如 `--reload-dir backend`；
- 如果前端需要自动刷新，再单独加前端开发服务器，不要让后端承担前端热更新。

**验收**

- 安装主程序依赖时只装一个 MySQL 驱动；
- 修改 `scripts/` 不会重启 API；
- 运维脚本仍可运行。

### P2：补齐数据库约束和可观测性

当前 schema 有主键、外键和部分索引，但缺少：

- 支付状态枚举或检查约束；
- 库存、数量、金额的非负约束；
- 慢查询、锁等待、备份失败告警；
- 结构化审计字段（操作人、请求号、action_id）。

这些不是当前业务闭环的阻塞项，但在多端接入或对外服务前应补上。

## 5. 外部评审的“下一步路线”应该怎么落地

评审建议继续做 AI 员工，方向是对的，但顺序要收窄。不要先接模型，再补规则和测试。

### 阶段 A：先把 AI 的确定性底座做出来

只做以下四件事：

1. `ai/policy/store_policy.json`：折扣、取整、时区和会员规则；
2. `ai/policy/policy_engine.py`：`Decimal` 计算和规则测试；
3. `get_hall_overview()`、`get_daily_report()` 两个只读工具；
4. CLI 打印 JSON，先验证数字和数据库一致。

这个阶段不接大模型，也不允许 AI 写数据库。

### 阶段 B：只读老板助手

接入模型前，先准备 20-30 条工具选择评测，覆盖：

- 今天营业额；
- 某商品销量；
- 未支付订单；
- 在开桌台；
- 时间范围和跨天口径；
- 模型不该编造数字的场景。

验收标准是“工具调用正确、数字来自数据库、模型不自行心算”。

### 阶段 C：受控写操作

只有在阶段 A/B 稳定后，才做：

- `prepare_*`；
- 服务端 `action_id`；
- 用户确认；
- `execute_action`；
- 幂等键和审计。

这也解释了为什么当前项目还不是“AI 员工已完成”：底座和业务写路径已经具备条件，但 AI 层还没有代码。

## 9. 一页结论

这套项目最值得保留的不是“技术栈数量”，而是下面这条思路：

> **先判断一个结果是否会被下一步读到；会，就留在主路径并保证写入；不会，才放旁路，并且为旁路准备检查和补偿。**

它已经体现在开台、关台、建单、收款和库存扣减的代码里，也体现在两篇设计文档里。

接下来最重要的工作不是继续加 Redis、加消息队列或堆 AI 概念，而是把现有承诺补齐：

1. 轮换凭据；
2. 保护测试库；
3. 消除业务层 IO 泄漏；
4. 补上备份缺口检查；
5. 定义 API 错误契约；
6. 用 `Decimal` 管理金额；
7. 再做有证据的并发测试；
8. 最后进入 AI 工具和规则引擎。

做到这些，项目才配得上“生产级准备”这个说法；在那之前，更准确的评价是：**边界意识很强、工程习惯正在形成、核心闭环已经成立的单店全栈项目。**
